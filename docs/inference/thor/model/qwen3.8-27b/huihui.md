# Huihui Qwen3.8-27B：NVFP4 试验与 DFlash2 性能剖析

[Thor 概览](../../README.md)

试验日期：2026-09-12。

在版本 `43aa7ff5eef05ab50a3bfa6aca581085312c7a04` 上测试了去拒答检查点
`Vtuber-plan/Huihui-Qwen3.8-27B-abliterated-NVFP4`。普通解码与 DFlash2 均在 Thor 上成功加载，
使用与[原始模型复测](original.md#保留的实验配置)相同的固定镜像版本、草稿模型和通用服务设置。
目标模型额外使用 `--quantization modelopt` 和 `--tool-call-parser qwen3_coder`。
加载器报告 `modelopt_fp4`、NVFP4 和 19.70 GiB 权重内存占用。尽管检查点也提供了 FP8 缓存缩放系数，
KV 缓存仍为 BF16。

沿用相同的三个提示词、token 上限、缓存清空、预热、三轮测量及流式解码速率计算方式。
请求明确设置 `enable_thinking=false` 和 `reasoning_effort=medium`。测量期间已停止原始模型服务，
下载也已完成。抽查显示 CPU 空闲率约 92–93%，I/O 等待为零，且未使用 swap；这些并非连续遥测记录。

| 目标模型与配置 | 中文 | 短代码 | 长代码 |
| --- | ---: | ---: | ---: |
| 原始模型 NVFP4，不使用推测解码（先前复测） | 13.04 | 13.04 | 13.01 |
| Huihui NVFP4，不使用推测解码 | 15.24 | 15.24 | 15.19 |
| 原始模型 NVFP4，DFlash2（先前复测） | 20.50 | 44.95 | 55.92 |
| Huihui NVFP4，DFlash2 | 19.36 | 62.26 | 58.78 |

这些结果不能单独识别去拒答处理的影响：两个检查点在量化与导出细节、聊天模板和生成文本方面也有差异。
Huihui 试验明确选择了中等推理强度，而先前原始模型的吞吐量请求只关闭了思考模式。
其模型卡记录了修改后的聊天模板。因此，解码速度提高不能仅归因于去除拒答。

使用 DFlash2 时，Huihui 的短代码吞吐量提高约 39%，长代码提高 5%，中文则下降 6%。
调度器采样窗口报告的接受长度，中文约为 1.8–2.0，长代码约为 5.7；这些只是示例窗口，
并非整次运行的平均值。修改目标模型后草稿模型仍有用，但收益高度依赖工作负载。

原始检查点的速度已远低于外部报告的 125–133 tokens/s，换成 Huihui 也未消除差距。
因此，这个特定的去拒答检查点无法解释此前已有的差距。这并非外部基准测试的复现：
本地尚未匹配其准确提示词、token 统计方式、模型版本和完整运行时配置。

## 功能冒烟检查与保留状态

两种 Huihui 配置均通过了中文指令、严格 JSON 值、结构化工具调用参数和思考模式开关的小规模检查。
工具并未实际执行。这些检查不能评估拒答率、整体模型质量或长上下文可靠性。

一个区间合并提示词暴露了相邻整数区间的歧义；原始模型和 Huihui 的输出最初都未通过六个功能用例中的两个。
在明确要求区间重叠或共享端点后，移除 Markdown 代码围栏的 Huihui 输出，无论是否使用 DFlash2，
均通过六个用例。但它们仍违反了不输出代码围栏的指令。原始服务未启用工具调用解析器，
因此缺少结构化工具调用字段不能证明其模型能力较差。

计时结束后恢复了原始服务。Huihui DFlash2 试验服务保留在独立的回环端口上；
两个健康检查均返回 HTTP 200。服务仍处于实验阶段，未配置自动启动。
固定版本的启动脚本、原始响应、基准测试轮次和服务日志保存在公开仓库之外。

## 试验后的后续建议

1. 统一比较协议：取得外部部署准确的目标/草稿模型版本、镜像与启动参数、提示词、思考模式、
   输出长度及 TPS 定义。本地分别记录 TTFT、端到端 TPS、解码 TPS 和每次验证步骤接受的 token 数。
   不要将八请求汇总吞吐量与单路流式吞吐量比较。
2. 对固定的目标模型和工作负载进行性能剖析，区分草稿生成、目标验证和主机调度时间。
   同时记录实际 GPU/EMC 时钟、功耗和热限制。这应有助于区分草稿接受率低与验证或调度成本高；
   目前尚不能确定哪一个是主因。
3. 在相同目标模型和明确的模板设置下，测试更长的英文及中文代码生成，按需增加并报告上下文预算。
   同时测试可预测性较低的散文。保留 token 数和接受率统计，不要只挑最快的提示词。
4. 根据测量结果，每次只选择一项运行时改动：兼容的 SGLang/内核版本、后端或受支持的推测解码设置。
   此镜像中的全模型 FA4，以及结合 `torch.compile` 的 DFlash2 已经失败；
   只有在有证据表明具体故障已解决时才重试。

## DFlash2 性能剖析与输出投影后续研究

两次短时 Huihui + DFlash2 性能剖析各捕获了十一次早期推测解码迭代，不含预填充。
CUDA 图 ID 和启动关联信息可区分草稿生成与目标验证；仅靠标注名称做不到这一点。

| 每次推测迭代的 GPU 耗时中位数 | 中文 | 长代码 |
| --- | ---: | ---: |
| 完整迭代 | 95.43 ms | 97.50 ms |
| 草稿图 | 23.36 ms | 23.70 ms |
| 目标验证图 | 69.67 ms | 71.31 ms |

相邻迭代的间隔与这些 GPU 耗时接近。CPU 事件同步主要是在等待 GPU，而非执行额外计算。
采样工作负载由矩阵运算主导：草稿内核时间约 97% 为 BF16 GEMM/归约，目标内核时间约
76% 为 NVFP4 GEMM、14% 为 BF16 GEMM/归约。内核耗时可能重叠，不能直接相加作为总耗时。
GPU 时钟维持在约 1385–1386 MHz，EMC 为 4266 MHz，GPU 温度低于 56 C。
这些观察尚不能证明内存带宽饱和或存在绝对吞吐量上限；性能剖析器开销也未经校准。

两张图都包含一个网格为 `(1940,1,1)`、耗时约 9.75 ms 的 BF16 投影。
输出词表有 248320 项，恰好是 1940 个 128 项的块。在 Thor 上进行的独立 CUDA 图微基准测试，
以 5120 的隐藏层维度复现了相同的全词表内核 `nvjet_sm110_tst_128x8_64x12_2x1_v_bz_TNT`：

| 词表项数 | BF16 输出头大小 | 7 行 | 8 行 |
| --- | ---: | ---: | ---: |
| 248320 | 2.368 GiB | 9.676 ms | 9.669 ms |
| 65536 | 0.625 GiB | 2.556 ms | 2.555 ms |
| 32768 | 0.313 GiB | 1.339 ms | 1.337 ms |

独立测试使用 Torch 2.13.0+cu130；每种形状先进行五次 eager 预热和五次图预热，
再进行二十次 CUDA 事件测量，并且每次只分配一个输出头。GPU 频率为 1386 MHz，温度为 34–35 C。
这有力支持耗时来自输出头的判断，但无法事后为原始追踪补上缺失的形状/模块标签。

因此，仅缩小草稿模型词表是一个具体的后续实验。它必须使用独立输出头，并将采样 ID 映射回原始词表；
目标模型的完整输出头和验证过程必须保持完整。先用中文、英文和代码提示词测量贪心解码，
记录接受率及总迭代时间。微基准测试并未测量这些结果。即使完全消除草稿投影，
在剖析的 97 ms 迭代中也仅节省约 10 ms，理想化吞吐量增益约 11%；
它本身无法解释与外部 125–133 tokens/s 报告之间的差距。
