### 检查点来源与布局

镜像中的两个检查点均为公开、无需申请访问权限的 Apache-2.0 Hugging Face 工件。镜像固定了确切的修订版本，而非可变的分支名称：

- [joshebbs/qwen3.8-27b-uncensored-nvfp4-modelopt](https://huggingface.co/joshebbs/qwen3.8-27b-uncensored-nvfp4-modelopt/tree/e5ff4986938dcd0dd05ab4cce89da1b052be6ce3),
  修订版本 `e5ff4986938dcd0dd05ab4cce89da1b052be6ce3`；
- [maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal](https://huggingface.co/maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal/tree/bd7a934213c47a9e7ef69eef36bb3325f47fd1f1),
  修订版本 `bd7a934213c47a9e7ef69eef36bb3325f47fd1f1`。

目标模型的 19,743,750,248 字节主权重的 Hugging Face LFS SHA-256 为
`5db0ff93ebdf68034770a6acec123971e618928684bd2d5f3f51346990254911`.
849,400,424 字节的嫁接 MTP 权重的 SHA-256 为
`90fa0e3eed5a647c035c6df9ecabc416c0f8d573ff84ac12485b085f00a7cdf2`.
1,550,153,248 字节草稿模型的 SHA-256 为
`2228b9b22e93a88d84556419c879448ab6c490ae65c4c0b166f4962190ddbf26`.
主目标模型和草稿模型的哈希值均与运行时镜像标签及从镜像提取的文件一致。因此，官方部署逐字节使用了已发布工件；未发现 Lazycat 专属的权重差异。

此目标模型并非当前生产检查点的另一种打包形式。其来源是
[JonathanColetti/Qwen3.8-27B-Uncensored](https://huggingface.co/JonathanColetti/Qwen3.8-27B-Uncensored),
即 Qwen3.8-27B 的消融拒答变体。该仓库将主语言模型的 400 个线性层量化为采用 K16 分块和 FP8 缩放的校准 NVFP4 W4A4。DeltaNet 的 `in_proj_a`、`in_proj_b` 和 `conv1d`，以及输出头、视觉塔和 MTP 头，仍使用 BF16。校准使用了 256 个最长 1,024 token 的 Open-Platypus 样本，之后未再微调。由于检查点每字节打包存储两个 4-bit 值，普通的 Transformers 加载方式无效；运行时必须理解 ModelOpt FP4 布局。

五层 DFlash2 草稿模型将其 35 个线性投影量化为校准后的 NVFP4 W4A4 K16。其目标特征 `fc` 和动态卷积投影仍为 BF16。模型卡报告称，使用 460 段对话进行了 on-policy 校准，接受长度为 3.60/8；未经校准的就近舍入 NVFP4 为 3.26/8，原始 BF16 草稿模型为 3.71/8。最终输出哪些 token 仍由目标模型验证决定；草稿模型量化主要改变草稿计算成本、内存占用和接受情况。

当前生产环境中的模型组合具有不同的来源和精度分配：

| 检查点组合 | 目标模型布局 | 草稿模型布局 | 权重字节数 |
| --- | --- | --- | ---: |
| 当前生产配置 | 原版 Qwen 目标模型；208 个 attention/DeltaNet 投影使用 FP8，192 个 MLP 投影使用 NVFP4，输出头使用 BF16 | BF16 z-lab DFlash2；运行时应用本地 INT8 输出头优化 | 27,598,150,584 |
| Lazycat | uncensored 目标模型；400 个主要投影使用 NVFP4，精度敏感部分除外 | 校准后的 NVFP4 DFlash2 | 22,143,303,920 |

Lazycat 模型组合小约 5.08 GiB，因此为 KV 缓存留出更多统一内存；但这也意味着吞吐量和生成 token 的差异不能只归因于推理服务引擎。目标模型的语义权重、目标模型量化及草稿模型量化均发生了变化。

两个目标模型目录具有相同的聊天模板、词表、新增 token 和语义 BPE 合并表。但其 tokenizer 序列化并不完全相同：填充 token、组合附加符号的预分词表达式及 ByteLevel 标志存在差异。常见基准文本预计会得到相近的分词结果，但边界 Unicode 情况和批量填充仍是额外变量。

无需使用 Lazycat 镜像，也可通过以下命令下载这一确切的模型组合：

```console
hf download joshebbs/qwen3.8-27b-uncensored-nvfp4-modelopt \
  --revision e5ff4986938dcd0dd05ab4cce89da1b052be6ce3 \
  --local-dir ./qwen38-lazycat-target
hf download maurienne-ai/Qwen3.8-27B-DFlash2-NVFP4-RTNcal \
  --revision bd7a934213c47a9e7ef69eef36bb3325f47fd1f1 \
  --local-dir ./qwen38-lazycat-draft
```

主要推理服务配置：

| 设置 | 观察值 |
| --- | --- |
| 调度器 | 8 个序列，4,096 个批处理 token，禁用异步调度 |
| 上下文 | 512,000-token YaRN 视图，由原生 262,144 扩展，系数 1.953125 |
| KV 缓存 | 44.5 GiB，容量 539,789 token，块大小 864 |
| 前缀缓存 | 已启用，使用 SHA-256 哈希 |
| 推测解码 | 量化 DFlash2 草稿模型，K16 |
| 编译 | Eager 执行；禁用 Torch compile 和 CUDA Graph |
| 量化 | 目标和草稿模型使用 ModelOpt NVFP4；目标模型线性层后端为 CUTLASS |
| Mamba 状态 | 缓存 dtype 为 `auto`；指标报告 FP32 SSM 状态 |
| 网络 / IPC | 主机网络模式 / 主机 IPC |
| 容器权限 | NVIDIA 运行时、`IPC_LOCK`、非特权 root |

vLLM 警告称，在 16-token 推测窗口下，4,096 个调度 token 的上限可能并非最优。封装程序还将 4 GiB GPU 内存限制转换为 `gpu_memory_utilization=0.032557`，而部署配置另行指定了 44.5 GiB 的 KV 分配。指标同时反映了两个值；实际缓存分配应由明确的 KV 容量描述，不能仅看百分比。

报告的 KV 容量仅相当于同时处理 1.054 个完整的 512,000-token 请求。因此，8 是短请求的调度器上限，而非同时处理 8 个最大上下文请求的容量。

镜像元数据宣称支持 900,000-token 配置，但此部署明确提供 512,000-token 服务。不能将镜像能力与已部署 API 的限制混为一谈。

## API 与能力观察

服务暴露 vLLM 的 OpenAI 兼容聊天、补全、responses、Anthropic messages、分词和指标路由。启动时未传入 API key 参数：不带认证、使用错误 bearer token 及使用已配置 token 的模型列表请求均返回 HTTP 200。模型进程也未启用 TLS。因此必须在外部提供网络访问控制。

目标模型配置包含视觉编码器，管理客户端宣称支持文本和图像输入。运行时启用了 Qwen3 推理解析器、Qwen3 XML 工具解析器和自动工具选择。DFlash2 启动日志指出，外部多模态 embedding 不会传入草稿模型；多模态请求对草稿模型使用纯文本输入。

限定范围的冒烟检查全部通过：

- 合成的 32 x 32 纯红色 PNG 在 0.357 秒内返回 `red`；
- 严格 JSON schema 请求准确返回 `{"answer":42,"label":"thor"}`；
- 自动工具选择请求生成了城市为 `Beijing` 的 `get_weather` 调用；
- 正常停止的 Python 请求生成了可解析代码，包含要求的五条断言。

这些检查确认了推理服务路径可用，但不能证明广泛的视觉、工具使用或代码质量。

## 单流测量

三个提示词及输出上限与[此前的本地实验](original.md#方法与结果)一致。每种负载先进行一次 32-token 预热，然后执行三次测量请求。温度设为零，禁用思考，并提供固定种子。服务没有重置前缀缓存的路由，因此每次请求使用独立的 `cache_salt`，在保持提示词完全相同的同时避免缓存复用。解码速率按 `(completion tokens - 1) / (stream end - first content)` 计算。

| 负载 | 输出上限 | 解码速率 | 中位数 | 首个内容延迟中位数 | DFlash 接受 / 提议 token |
| --- | ---: | --- | ---: | ---: | ---: |
| 中文 | 256 | 17.37, 17.40, 17.37 | 17.37 tokens/s | 0.152 s | 369 / 6,384 (5.8%) |
| 短代码 | 256 | 62.37, 62.38, 62.34 | 62.37 tokens/s | 0.148 s | 660 / 1,776 (37.2%) |
| 长代码 | 1,024 | 79.48, 79.49, 79.59 | 79.49 tokens/s | 0.153 s | 2,727 / 5,568 (49.0%) |

所有测量响应均达到长度上限，因此代码吞吐量并不代表完整代码的正确性结果。每种负载的三次响应具有相同哈希值，与同一测试期间观察到的非确定性 Flash Next 部署不同。

厂商产品页面公布的单流速率范围为 49–135 tokens/s。两种代码负载均处于该范围内；中文负载低于此范围，因为 DFlash 接受率仅为 5.8%。提示词和生成文本的可预测性会显著影响推测解码吞吐量。

## 八请求并发

先进行一批预热，再测量三批请求。每批同时提交八份短代码负载，输出上限为 128 token。独立的缓存盐防止请求间复用前缀。聚合解码统计从首个内容事件到最后一个流完成期间交付的所有 token。

| 批次 | 聚合解码速率 | 批次实际耗时 | 单请求解码速率中位数 | 单请求 TTFC 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 179.51 tokens/s | 5.828 s | 23.37 tokens/s | 0.387 s |
| 2 | 179.50 tokens/s | 5.823 s | 23.38 tokens/s | 0.385 s |
| 3 | 179.46 tokens/s | 5.823 s | 23.37 tokens/s | 0.384 s |

聚合速率中位数为 179.50 tokens/s，DFlash 在 8,880 个提议 token 中接受了 2,517 个（28.3%）。该速率比厂商展示的 182–423 tokens/s 范围下限低 1.4%；差距很小，因此确切提示词、输出长度和计时边界都会影响比较。

## 预填充与上下文容量

一次预热和三次测量请求均使用恰好 5,001-token 的聊天提示词及 32 个输出 token。独立的缓存盐强制重新计算全部提示词 token。首个内容延迟分别为 2.612、2.616 和 2.607 秒，中位数为 2.612 秒。vLLM 将其中 2.572–2.576 秒归于预填充，计算速率中位数约 1,941 tokens/s；排队时间仅为 8–12 微秒。

产品页面报告 5K 输入的 TTFT 为 2.49 秒，预填充速率为 2,133 tokens/s。观察到的 TTFT 中位数慢 4.9%，内部预填充速率低 9.0%。由于确切文本和计时定义可能不同，这只是观察性比较，不能视为受控的性能回归。

包含 500,001 个重复普通 token 和一个输出 token 的预分词请求成功完成。整个 HTTP 请求耗时 1,490.30 秒；vLLM 将其中 1,490.00 秒归于预填充，即 335.57 个计算 token/s，排队时间约 30 微秒，未发生抢占。活动 KV 使用率达到约 92.48%，请求完成后回落至零。

长上下文遥测覆盖了该请求的前 879 秒。报告的 GPU 功率平均为 69.05 W，峰值为 74.48 W；GPU 峰值温度为 69.9 C，系统 RAM 使用峰值为 78.15 GB。这些是传感器读数，并非整板输入功率。重复 token 提示词验证的是容量和运行时稳定性，不能验证长上下文检索或回答质量。

构造的 512,001 个输入 token 加一个输出 token 的请求在推理前于 0.077 秒内被 HTTP 400 拒绝。错误消息明确指出总上下文上限为 512,000 token。因此，此部署无法使用镜像的 900K 配置。

## 推理运行期间的进程快照

在八个并发请求均运行期间，采集了一份 root 级进程快照。vLLM 报告等待请求数和抢占次数均为零。Qwen 容器中有四个进程：

| 角色 | 进程 | 线程数 |
| --- | --- | ---: |
| 容器初始化及运行时入口 | `docker-init` | 1 |
| vLLM OpenAI API 前端 | `vllm.real serve` | 62 |
| Python 多进程资源跟踪器 | `multiprocessing.resource_tracker` | 1 |
| 模型执行进程 | `VLLM::EngineCore` | 110 |

完整的主机快照包含 485 个进程和 1,212 个线程。私有工件保留了 root 可见的完整命令行、可执行文件映射、进程树、Docker 进程列表、cgroup、命名空间、套接字及同期 GPU 状态；由于整机列表包含无关的环境特定信息，这些工件未放入公开仓库。

## 运行观察

此部署之后，算力舱根文件系统报告仅剩约 3 GiB 可用空间，使用率四舍五入后为 100%。测试没有额外消耗大量磁盘空间，但未来镜像更新、缓存写入和日志增长的余量很小。将此部署用作长期服务前应解决该问题。

空闲时，整机 125.8 GB RAM 中约有 77.9 GB 被占用，Qwen 容器报告普通 cgroup 内存占用约 7.0 GiB。500K 请求期间，系统 RAM 用量保持在约 78.1 GB，因为较大的 KV 空间已在启动时预留；活动 KV 块增加并未导致主机新增数十 GiB 内存分配。

## 测量现状与后续工作

本文已足以作为官方应用、单流及八请求解码、5K 预填充、API 能力、接近上限的容量和运行中进程布局的初步版本固定记录。后续值得进行的工作包括：

1. 在多个深度测试长上下文检索；重复 token 的容量请求无法衡量 YaRN 质量。
2. 在受控 A/B 测试中比较 eager 执行与经过验证的 CUDA Graph 配置，并提高 4,096 个调度 token 的上限。
3. 在将产品页面上的小幅差异视为性能回归前，获取厂商使用的确切提示词和计时定义。
4. 先确定安全的内存和磁盘预算，再复现镜像的 900K 配置；不要从成功的 500K 请求推断其可用性。

原始请求、计数器、遥测数据及进程清单均保留在公开仓库之外。

## 使用 Lazycat 检查点的本地 SGLang

同一台机器重启进入 NixOS 后，将官方镜像内置的目标模型和草稿模型复制到本地模型存储。复制所得的 `model.safetensors` 文件与镜像标签完全一致：

- 目标模型 SHA-256
  `5db0ff93ebdf68034770a6acec123971e618928684bd2d5f3f51346990254911`;
- 草稿模型 SHA-256
  `2228b9b22e93a88d84556419c879448ab6c490ae65c4c0b166f4962190ddbf26`.

本地运行时为 SGLang `0.0.0.dev1+g5f55db35e`。它使用原生 262,144 上下文、四个运行中请求、总计 270,336 个 token、BF16 KV、Triton attention 与 linear attention、FlashInfer CUTLASS FP4 GEMM、完整解码 CUDA Graph，以及现有的 Thor GDN 验证补丁。这与官方的 512K YaRN、八序列、eager vLLM 配置存在实质差异，因此跨运行时数据并非仅比较检查点的 A/B 实验。

### 上下文上限与 YaRN 的区别

管理界面称 512K 配置是最快的单流选项。为区分请求数值上限与其捆绑的 YaRN 模型视图，四种本地 SGLang 变体保持相同的 270,336-token KV 池、四个运行中请求上限、BF16 KV、K16 草稿模型及 CUDA Graph 设置。仅改变对外公布的上下文上限和目标模型 RoPE 配置。测试使用相同的一次预热加三次短请求测量流程。

| 对外公布的上限 | 目标模型 RoPE 视图 | 中文 | 短代码 | 长代码 | 输出哈希组 |
| ---: | --- | ---: | ---: | ---: | --- |
| 262,144 | 原生 262,144 | 21.42 tok/s | 68.79 tok/s | 88.10 tok/s | A |
| 512,000 | 原生 262,144 | 21.37 tok/s | 68.62 tok/s | 87.90 tok/s | A |
| 512,000 | YaRN 512,000, factor 1.953125 | 21.98 tok/s | 67.04 tok/s | 87.95 tok/s | B |
| 262,144 | YaRN 512,000, factor 1.953125 | 21.94 tok/s | 67.04 tok/s | 88.01 tok/s | B |

对每种负载和每次重复，若只将上限从 262,144 改为 512,000，输出哈希保持不变，解码速率差异不超过 0.25%。反过来，将 512K YaRN 视图置于 262,144 的上限之下，也保留了相应 512K 配置的输出哈希，速率差异在 0.19% 以内。因此，观察到的行为取决于 YaRN 配置，而非上下文上限数值。

这并不证明 YaRN 使内核本身更快。它改变旋转位置编码频率，进而即使对短提示词也会改变 logits、生成 token 轨迹和 DFlash 接受情况。相对于原生 262K，512K 视图使三种速率分别变化约 +2.6%、-2.5% 和 -0.2%；900K 视图分别变化 +1.8%、-11.3% 和 -7.7%。在八请求短代码批次中，512K 视图的聚合速率比原生 128K 视图快 4.2%，而 900K 视图慢 14.1%。这些是随负载而变的推测解码效应，并非数值 512K 具有普遍优势。

对照实验固定了物理 token 池，测试的是短提示词。它没有检验超出原生 262K 范围后的质量，也没有测量实际占满 512K 上下文时的内存与预填充成本。512K 这个确切数值只通过所选 YaRN 系数及官方预设中捆绑的其他设置间接发挥作用。

覆盖短解码、八路负载和长预填充探测的 829 个一秒遥测样本显示，活动 GPU 时钟保持在 1,385--1,386 MHz。GPU 峰值温度为 57.2 C，控制器观察到 39--57 C 并选择 PWM 102--147，报告的 GPU 供电轨功率峰值为 110.7 W，RAM 用量最大值为 77,179 MiB。未发生 OOM、Xid 或内存保护事件。之后停止了临时模型和遥测单元，仅风扇控制保持运行。

当前生产配置和 Lazycat K16 均正确发出了自动 `get_weather` 调用，JSON 参数为 `{"city":"上海"}`。每种测试配置内部的三次测量输出哈希完全相同。然而，尽管温度为零且种子固定，仅目标模型、K8 和 K16 的输出彼此不同。可见内容仍然合理，但推测解码路径与仅目标模型的生成结果并非逐字节相同。替换生产配置前仍需进行正确性和质量验证。

### 本地长上下文验证

随后，Lazycat K16 组合在同一本地 SGLang 配置下通过了限定范围的 32K、64K 和 128K 检索检查。每份合成归档均在填充内容约 5%、50% 和 95% 的位置放置准确值 `cobalt-7319`、`willow-4826` 和 `silver-9053`。提示词大小通过运行中服务器的 `/tokenize` 路由校准，并非仅根据离线 tokenizer 推断。每个测试用例都先清空前缀缓存。

每个长度执行两个独立的冷请求。schema 请求禁用工具选择，要求返回恰好包含三个字符串字段的对象。工具请求暴露 `record_vault`，要求恰好发出一次自动调用，并以这些字段作为参数。Qwen 将工具定义放在用户归档之前，因此两类提示词的开头 token 不同，不能复用彼此的 radix 缓存前缀。

| 路径 | 输入 token 数 | 首个内容 | 完成耗时 | 输出 token 数 | 结束原因 | 检索结果 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 严格 JSON schema | 32,767 | 30.906 s | 32.077 s | 36 | `stop` | 3/3 |
| 自动工具调用 | 32,767 | 31.337 s | 32.753 s | 69 | `tool_calls` | 3/3 |
| 严格 JSON schema | 65,535 | 107.390 s | 109.264 s | 45 | `stop` | 3/3 |
| 自动工具调用 | 65,537 | 108.475 s | 111.115 s | 69 | `tool_calls` | 3/3 |
| 严格 JSON schema | 131,072 | 396.082 s | 401.321 s | 36 | `stop` | 3/3 |
| 自动工具调用 | 131,073 | 397.953 s | 402.557 s | 69 | `tool_calls` | 3/3 |

所有 schema 响应均可解析为准确要求的对象。所有工具测试均发出一次 `record_vault` 调用，其解析后的参数与该对象完全一致。128K schema 的 TTFC 与当前生产检查点此前 397.149 秒的冷归档结果相差不超过 0.3%，尽管提示词及结构化输出约束并不完全相同。因此，更换检查点并未显著改善占主导地位的 128K 冷预填充成本。随着上下文翻倍，TTFC 的增长也远快于输入长度：约为 31、107 和 396 秒。对这类负载，长预填充比短解码更值得优化。

服务报告的提示词长度也解释了表面上的工具路径成本。32K 的两个请求输入长度相同，而工具请求在 64K 仅多两个 token，在 128K 仅多一个。使用测试中的 1024-token 预填充块时，这些微小增加恰好跨越分块边界：65,535 与 65,537 分别需要 64 与 65 块，131,072 与 131,073 分别需要 128 与 129 块。因此，观察到的工具/JSON TTFC 差异不能归因于解析器或语法引擎；额外的短尾块是直接的混杂因素。

再次清空缓存后，一个冷 128K schema 请求在首次输出前的 15.011 秒断开连接。五秒后，短请求在 0.665 秒内返回 `THOR_CANCEL_OK`。日志显示，长预填充在仍有约 108K 个 token 待处理时停止，随后执行了短请求的 18-token 预填充，证实打补丁后的断开连接路径释放了执行槽位。

实验侧监控程序每秒采样一次主机内存，并在整个试验期间应用生产环境的保护阈值。在 1,440 个样本中，`MemAvailable` 最低为 61.13 GiB，`MemFree` 最低为 15.20 GiB，空闲交换空间最低为 30.71 GiB。没有触发任何阈值。这说明这些单请求 128K 用例具有充裕余量，但不代表任意并发长提示词都安全。随后恢复了常规生产 SGLang 服务、内存监控和健康检查定时器；HTTP 健康检查返回 200，且没有内存停止锁。

这些检查验证了截至 128K 的合成深度检索、schema 约束、工具参数构造和客户端取消。它们没有衡量广泛的长上下文推理、仓库规模的代码质量或多个同时发生的冷预填充。

### 分块预填充筛选

后续单变量筛选保持 Lazycat K16 组合、Triton attention 后端、BF16 缓存、禁用预填充 Graph，以及恰好 65,535-token 的 schema 测试样本不变。候选配置先完成一次 16K 预热，再清空 radix 缓存并执行测量请求。此前的 1024 结果使用相同测试样本哈希，但来自前一阶段的长上下文验证，并非本次筛选流程。

| 块大小 | 冷 64K 首个内容耗时 | 完成耗时 | 重复次数 | 检索结果 |
| ---: | ---: | ---: | ---: | --- |
| 1024 | 107.390 s | 109.264 s | 此前基线 1 次 | 3/3 |
| 2048 | 104.139, 104.194 s | 106.016, 106.071 s | 2 | 3/3 |
| 4096 | 104.214 s | 107.223 s | 1 | 3/3 |
| 8192 | 105.628 s | 108.259 s | 1 | 3/3 |

2048 配置的两次重复仅相差 0.055 秒，相对于 1024 将首个内容延迟改善了约 3.0%。将块增至 4096 未进一步改善首个内容延迟，而 8192 又趋近基线。结果只表明此实现中所筛选数值带来有限收益；不能据此断定块大小只能影响常数项或线性项。精确因果注意力在任何块大小下的 token 对总数相同，但内核效率或重复前缀准备仍可能改变测得的二次项系数。

对测量运行中的完整块进行回归分析，也支持这一区别。按先前前缀长度拟合的每块斜率，在块大小 2048 时为每个前缀 token 76.6 微秒，在 4096 时为 145.2 微秒，在 8192 时为 255.9 微秒。各斜率除以对应块大小后数值相近，而完整块总耗时分别保持在约 106.0、106.1 和 107.5 秒。因此，本次筛选未发现增大服务分块能消除占主导地位的前缀相关工作。下文的 128K 及混合负载测试表明，若交互式解码延迟重要，应保留 1024。

相同的启动过程还揭示了两个有用的实现事实。每次加载目标模型都恰好记录 48 次成功的 SiLU+mul+FP4-quant 融合，对应 48 个 Gated DeltaNet 层；源码检查表明，16 个全注意力稠密 MLP 并不调用同一个融合初始化器。FlashInfer FP4 自动调优已在 SM110 上启用，并为目标模型和草稿模型加载了架构及环境专属缓存。因此，后续策略调优应先确认实际推理服务中缺失的形状，不能假定部署只使用单一未经调优的 CUTLASS 策略。

### 内核级预填充归因

一份 Nsight Systems 2026.4.1 跟踪记录单独分析了块大小为 1024 时一次正确的 65,535-token schema 请求。它返回了全部三个事实，108.220 秒出现首个内容，110.099 秒完成。未采样分析的基线为 107.390 秒，因此性能分析使 TTFC 增加约 0.8%。

跟踪中恰有 1,024 次 Triton `_fwd_kernel` 启动，即 64 个块乘以模型的 16 个全注意力层。它们耗时 89.243 秒，占观察到的 TTFC 的 82.5%，占 GPU 内核时间总和的 84.1%。以块索引回归每块累计注意力时间，得到 `-11.444 + 44.631 * index` 毫秒，R 方为 0.99947。对应的整块 GPU 时间窗口随索引每增加一格增长 44.920 毫秒，R 方为 0.99937。因此，全注意力解释了测得的前缀相关斜率的 99.4%。

其他 GPU 项目每块耗时基本持平：FP4 GEMM 约 100.8 毫秒、GDN 约 65.7 毫秒、FP4 量化约 24.3 毫秒、归一化/RoPE/激活约 36.1 毫秒、BF16 GEMM 约 16.9 毫秒。GPU 时钟保持在 1,385--1,386 MHz，EMC 为 4,266 MHz，温度为 53.6--64.3 摄氏度。`MemAvailable` 最低为 55.14 GiB，实验内存保护未触发。这排除了持续性的热降频，并将观察到的几乎全部超线性增长归于全注意力预填充内核，而非 GDN、GEMM、草稿模型物化或主机调度。

请求期间的进程快照包含预期的 Nsight 封装进程、tokenizer、调度器、detokenizer、编译 worker 和基准测试客户端。原始跟踪、遥测及 root 可见的进程快照包含主机细节，因此保持私有。

### FlashInfer 预填充正确性筛选

对 SGLang PR #39811 的最小化回移植仅修改了 SM110 后端门控。实验仍将 Triton 用于目标模型解码、草稿模型注意力和全部 GDN 阶段，仅在目标模型全注意力预填充中选用 FlashInfer。服务器使用已安装的 FlashInfer 0.6.17 成功启动，日志记录了预期选定的后端。

第一次 16,386-token 正确性请求在 6.932 秒出现内容，8.422 秒完成，但三个哨兵值一个也未检索到，反而返回无关的提示词片段。因此测试程序在计划的 64K 计时前停止。没有发生服务器崩溃、OOM、Xid 或温度事件。此路径速度快得多，但在已安装的软件栈上不可用；这也印证了 PR #39811 的警告：其 Thor 测量并未证明精度一致。

依赖升级筛选随后在隔离镜像中安装官方 FlashInfer 0.6.18 的 Python、cubin 和 JIT 缓存 wheel，同时保留 Torch 2.13.0+cu130、Triton 3.7.1、相同的 SGLang 提交及相同的阶段划分。16,386-token 请求再次失败，解析后的输出及输出哈希与 0.6.17 完全相同：返回 `{"alpha":"1024","beta":"filler","gamma":"cobalt-60"}`，而不是三个哨兵值。TTFC 为 6.810 秒，完成耗时 8.287 秒。两个版本出现完全相同的错误输出，比仅 0.6.17 存在打包缺陷更有力地指向路径级正确性问题。因此也排除 FlashInfer 0.6.18，无须再花时间测量 64K 或 128K。参见 [0.6.18 发布页](https://github.com/flashinfer-ai/flashinfer/releases/tag/v0.6.18)和[安装文档](https://docs.flashinfer.ai/installation.html)。生产源码及依赖均未更改。

### FA4 源码验证

镜像既包含 site-packages 下的 `flash-attn-4` 4.0.0b19，也包含 SGLang 内置的 FA4 源码树。两个副本仍保留拒绝 `seqused_q/seqused_k` 的 head-dimension-256 前向断言；均未包含 #2810 对 paged-KV 范围的取整修复，也未包含 #2880 的 `domain_offset_aligned` 及单元素 stride 对齐改动。因此，已安装的 FA4 路径未通过最初的源码门槛。

### SM110 Triton 调优

固定版本的 Triton extend-attention 配置在此 SM110、QK/V head dimension 为 256 的形状下，使用 `BLOCK_M=64`、`BLOCK_N=64`、八个 warp 和一个流水线阶段。源码挂载实验仅修改这一形状，保持 Lazycat K16 模型组合、1024-token 服务分块、BF16 缓存及其他所有后端不变。

| Extend-attention 配置 | 冷 64K 首个内容耗时 | 完成耗时 | 结果 |
| --- | ---: | ---: | --- |
| 固定版本 `64x64`，1 阶段 | 107.390 s | 109.264 s | 3/3 |
| `128x64`，1 阶段 | 75.099, 75.101 s | 77.354, 77.356 s | 两次均 3/3 |
| `128x128`，1 阶段 | 75.034 s | 77.290 s | 3/3 |
| `128x64`，2 阶段 | 69.225, 69.562 s | 71.297, 71.630 s | 两次均 3/3 |
| `128x64`，3 阶段 | 未运行 | 未运行 | 编译被拒绝 |

将 `BLOCK_M` 翻倍，使每个 Q head 独立流式读取前缀 KV 的查询程序数量减半，并使 64K TTFC 降低约 30%。将 `BLOCK_N` 翻倍没有带来进一步的实质变化。增加第二个流水线阶段，使两次运行均值降至 69.393 秒，比固定版本基线低 35.4%。三个阶段需要 262,688 字节共享内存，超过 Thor 的 232,448 字节上限，因此在测量请求前就被拒绝。两次 stages=2 重复相差 0.337 秒，解析值和输出哈希完全相同。

在 128K 下，收益进一步增加：

| 路径 | 固定版本 TTFC | 调优后 TTFC | 调优后完成耗时 | 检索结果 |
| --- | ---: | ---: | ---: | --- |
| 严格 JSON schema，131,072 tokens | 396.082 s | 242.556 s | 247.660 s | 3/3 |
| 自动工具调用，131,073 tokens | 397.953 s | 246.278 s | 251.428 s | 3/3 |

这相当于 schema TTFC 降低 38.8%，工具 TTFC 降低 38.1%。调优后的 128K schema 运行保持 GPU 时钟在 1,385--1,386 MHz，最高温度为 65.7 摄氏度，`MemAvailable` 至少为 61.09 GiB，未触发内存保护。客户端在 15 秒时断开连接仍释放了长请求；经过五秒观察延迟后，短请求在 0.663 秒内返回 `THOR_CANCEL_OK`。

首个混合负载测试还暴露了单独 TTFC 测量无法体现的调度器行为。在相同的冷 64K 预填充之前，启动两个 `ignore_eos` 解码请求，每个均强制输出 1,024 token：

| 内核 / 调度器 | 64K TTFC | 解码间隔 p95 | 最大解码间隔 | 解码完成耗时 |
| --- | ---: | ---: | ---: | ---: |
| 固定版本，间隔 0 | 108.716 s | 107.963 s | 107.963 s | 148.992 s |
| 调优后，间隔 0 | 70.323 s | 69.706 s | 69.706 s | 111.005 s |
| 调优后，间隔 1 | 77.274 s | 1.937 s | 2.449 s | 111.262 s |

使用默认的 `prefill_decode_interval=0` 时，两条解码流在预填充期间各只收到六次 payload 事件，且各出现一次接近 TTFC 长度的间隔。内核改进缩短了这种饥饿状态，但未解决它。将现有调度器选项设为 1 后，每批预填充之后执行一轮解码：两条流在预填充期间分别收到 65--66 次事件，间隔中位数为 1.25--1.27 秒。这使混合负载的预填充 TTFC 增加 9.9%，但解码请求的总完成时间基本不变。对于交互式服务，这是经过验证的调度候选；只有明确优先考虑孤立预填充延迟时，间隔 0 才合适。此时尚未将调优内核或调度器选项安装到受管理服务中。

随后通过直接算子测试，在 BF16、GQA 24:4、head dimension 256 和 1,024-token 查询条件下，比较前缀长度为 0、32K、64K 和 128K 时的固定版本与调优后内核。两个内核在重复运行中均逐位稳定。6,291,456 个输出元素中，仅 31--38 个在两内核间不同。无前缀时最大绝对差异为 `2.44e-4`，非空前缀时最多为 `1.53e-5`（64K 和 128K 时为 `7.63e-6`）；没有 NaN 或无穷值。所有用例均通过 `atol=2e-2, rtol=1e-2`。每个长度抽样的九个 query/head 位置相对于独立 FP32 参考实现也具有相同的误差界限。

额外的 26 用例边界矩阵在前缀 0 和 128K 下测试了查询长度 1、17、63、64、65、127、128、129、255、256、257、511 和 1,023。它揭示了一项重要的适用范围修正：对长度不超过 64 的查询使用 128 行 tile，会使长前缀调用慢 34--36%。该范围包含推测解码验证批次。因此，最终候选在 `max_len_extend <= 64` 时保留固定版本的 `64x64`、单阶段路径；仅在 SM110、QK/V head dimension 为 256 且 `max_len_extend > 64` 的常规 `_fwd_kernel` 调用中使用 `128x64`、八个 warp 和两个阶段。带条件保护的候选通过完整矩阵，短查询输出也与固定版本路径逐位一致。

### 独立评审来源

本次调查使用了多轮模型辅助工作。这里记录各自角色，避免将建议误认为测量结果：

- **GPT-6-Astra Medium** 完成了本文记录的早期部署检查、基准测试构造及初步分析。
- **GPT-5.6-Sol xhigh** 完成了当前的本地与源码验证、性能分析、受控的后端/tile 实验，以及测量结果综合。
- **Claude Opus Max** 通过操作员提供的对话记录给出了独立的源码级批评。它审查了固定版本的 SGLang、FlashInfer 和 Triton 代码，并质疑最初的优化顺序。
- **GPT-6-Pro WebChat** 通过[共享回复](https://chatgpt.com/s/t_6aacfb01d0cc8191b647e1c2ee48a113)提供了第二份独立评审。最终答复及其中的研究报告均已检查。

模型评审提供的是线索，并非基准测试证据。下文论断要么有上述本地测量支持，要么经过固定版本源码/运行时验证，要么明确保留为实验假设。两份外部评审独立认为，用三点拟合三个参数的二次函数只是插值，而非证明：它强烈提示应调查全注意力，但单凭此拟合不能将二次项所占比例归因于注意力内核。

目标模型配置包含 16 个全注意力层和 48 个 Gated DeltaNet 层。全注意力是模型固有的二次复杂度 GPU 操作；GDN、MLP 和正常的增量草稿模型物化均随新增 token 线性增长。独立跟踪现已测得全注意力是主要成本，也是几乎全部前缀相关增长的来源。但跟踪本身不能区分内核内部是低效的 tile 划分、冗余 KV 流量，还是其他设备级原因。

### 修订后的优化研究方向

综合证据改变了后续工作的优先顺序：

1. 冷 64K 时间线已将 TTFC 的 82.5% 及其前缀相关斜率的 99.4% 归于全注意力，同时排除了热降频。较轻量的 128K 跟踪可作为可选确认，而非后端工作的前置条件。
2. 只修改目标模型预填充后端。截至 2026-09-18，尚未合并的 [SGLang PR #39811](https://github.com/sgl-project/sglang/pull/39811) 在 `5705691f4c3cdcc669cca04c7d19e14da8d607b9` 允许混合 GDN 模型在 SM110 上使用 FlashInfer 全注意力。其 Thor 证据使用 FlashInfer 0.6.18，报告的是共享前缀的输出吞吐量，而非冷预填充 TTFC；也未确立精度一致性。隔离的 0.6.17 回移植实现了所需阶段划分，在 16K 下速度很快，但在 64K 基准测试前就未通过检索。随后升级至官方 0.6.18 依赖，在 16K 下复现了完全相同的错误输出。因此，两种版本均不用于服务。FlashInfer 0.6.17 的另一条 CUTLASS FMHA 预填充分发路径也不接受该模型的 `(256,256)` QK/V head dimension。
3. 页大小为 128 的 FA4 b31 是已通过验证的受管理预填充后端。独立算子检查、重复的 schema/工具/取消测试组、12 个代表性请求和一/二/三条解码流的混合负载矩阵全部通过。相对于调优后的 Triton，它使 64K TTFC 降低 68.5%，128K TTFC 降低约 78%。其隔离且按哈希固定的 Python/TVM-FFI 层、针对 SM110 head dimension 256 的精确单分片保护、两小时受管理持续测试及冷重启恢复也全部通过。不要沿用实验性的全局确定性模式，也不要假定服务局部依赖覆盖层普遍兼容。
4. Triton 的 `128x64`、八个 warp、两个阶段的条件配置仍是已验证的回退后端。它通过了持续运行、混合负载和重启门槛，并使 128K TTFC 相比固定版本路径降低约 39%。不要将该 tile 推广到其他架构、head dimension 或短验证批次。
5. 将全注意力 MLP 的 SiLU+NVFP4 融合和仅打包 KV 的 DFlash 投影保留为次要的线性层/解码实验。前者可以节省 MLP 中间结果，却不能减少注意力 token 对；后者通常只影响新物化的草稿行。若性能分析发现整个前缀被重复处理，应先消除重复，再考虑仅缩小其投影宽度。FlashInfer cuDNN FP4 GEMM 也是实验性的线性层路径：已安装后端接受 SM110，但 SGLang `auto` 目前在此设备上选择 FlashInfer CUTLASS。
6. 当并发重要时，服务分块保持 1024。此前的 2048 筛选在孤立测试中节省约 3%，但默认调度使已有解码在整个长预填充期间饥饿。交互式部署使用 `prefill_decode_interval=1`。在 128K 下，调优后的 Triton 将观察到的间隔控制在 3.92 秒以下，FA4 候选将其降至 1.23 秒以下。保留检索、schema、工具、混合解码和取消检查作为正确性门槛。FA4 还要求 KV 页大小为 128。
7. 独立确定面向 uncensored 目标模型的 on-policy K16 草稿校准能否提高接受情况，同时保留量化草稿模型的内存与计算优势。这仍是质量与解码方面的调查，而非解决 396 秒预填充的办法。

FlashInfer PR
[#5302](https://github.com/flashinfer-ai/flashinfer/pull/5302) 明确排除在此长预填充研究路线之外：它是实验性的预处理 SM110 GQA 解码路径，并非适用于 `q_len=1024–8192`、head dimension 256 的因果预填充实现。

SGLang 在 1.7–1.9 秒内直接加载了量化草稿模型。由于融合的 DFlash KV 物化路径不支持该草稿模型的 ModelOpt FP4 QKV 投影，SGLang 禁用了该路径；未融合的回退路径仍产生了上述测量结果。K16 推理期间的进程快照包含 405 个主机进程。容器中包括 API 进程、多进程资源跟踪器、调度器、detokenizer、Torch Inductor 编译池及基准测试客户端。完整的 root 可见进程和 cgroup 快照包含无关的主机细节，因此保留在私有原始证据中。

确认了一项双系统启动时的运行风险：官方容器共用 NixOS Docker 存储，且原本使用 `unless-stopped` 重启策略，因此重启后可能与受管理的 SGLang 服务同时启动。实验使用了带独立清理流程的限定时长 systemd 单元。最终重启时，该容器在 `no` 重启策略下保持停止；只有受管理容器使用统一内存，且不存在内存停止锁。

这些结果验证了 Lazycat K16 可作为受管理的 NixOS 基线。它已通过截至 128K 的固定上下文检索、工具/结构化输出、内存余量、取消、混合负载和持续运行检查。由于目标模型来源及推测解码路径改变了确定性输出轨迹，仍值得在多样化真实负载上进一步评估质量。

截至 2026-09-19 已完成：直接算子一致性验证、带条件保护的短查询回退、代表性服务负载、一/二/三条解码流的 128K 混合矩阵、按哈希固定的运行时打包、完整 NixOS 系统的干净构建、机群自有性能配置复测、真正的八请求调度、两小时持续运行门槛、持续测试后的混合矩阵，以及已提升为受管理服务后的重启恢复。独立的后端筛选还因 16K 下相同的错误输出排除了 FlashInfer 0.6.17 和 0.6.18；随后通过算子一致性、重复的 16K/64K/128K 服务正确性、代表性负载、取消、一/二/三条解码流的混合负载、隔离的声明式依赖包、第二次两小时受管理持续测试及冷重启恢复，验证了 FA4 b31。后续匹配条件的 32K DFlash K16/K8/K4/无草稿模型筛选保留了 K16，将其与无草稿模型基线延伸测试至 128K，并排除了对分配和性能均无影响的 32K/8K 草稿窗口。后续按以下顺序进行：

1. 在日常使用中观察更广泛的真实代码/agent 负载。保留严格 schema、工具、取消、短请求延迟及一/二/三条解码流 128K 检查，作为回归门槛。
2. 除非有源码级正确性修复能够解释并消除重复出现的错误输出，否则继续排除 FlashInfer。MLP 融合、仅 KV 的草稿投影和草稿模型校准的优先级仍低于全注意力后端。
3. 将实际的 Triton 系统闭包回退视为可选的生产前演练，而非验证通过的阻碍。上游接受 SM110 head-dimension-256 验证形状后，移除或上游化局部的 FA4 单分片 workaround。

后端实验结束后，2026-09-19 的当前状态为：通过验证的 FA4 受管理系统闭包已安装，但由于操作员表示没有生产需求，推理服务、内存监视器和健康检查定时器已主动停止。性能风扇控制器仍在运行，官方及实验容器均已停止。
