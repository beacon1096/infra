## 方法与结果

每次只处理一个请求，上下文为 4096 个 token，设置 `temperature=0` 和
`chat_template_kwargs={"enable_thinking":false}`。每项工作负载先以 32 个输出
token 预热，随后测量三次。每个请求前都会清空前缀缓存。生成上限可能截断回复；
这是吞吐量测试，而不是完整的代码正确性评估。

| 工作负载 | 输出 token 上限 | 原始提示词 |
| --- | ---: | --- |
| 中文 | 256 | 用中文详细解释设备树如何帮助Linux启动，分五点说明，约400字。 |
| 短代码 | 256 | 请写一个Python函数判断整数是否是质数，并给出五个测试用例，然后解释时间复杂度。 |
| 长代码 | 1024 | 请实现一个完整的Python LRU缓存类，使用双向链表和字典，支持get和put，提供详尽的单元测试。直接输出代码，尽可能完整。 |

数值为三次运行的输出 token/s 中位数，计算方式为
`(completion_tokens - 1) / (stream_end - first_nonempty_content_chunk)`。
这是不含首个内容到达时间的流式解码估算值，并非端到端吞吐量；
一个推测解码流数据块可能包含多个 token。

| 配置 | 中文 | 短代码 | 长代码 |
| --- | ---: | ---: | ---: |
| 无推测解码 | 13.04 | 13.04 | 13.01 |
| EAGLE/MTP，步数/top-k/草稿 token = 3/1/4 | 19.61 | 31.14 | 29.56 |
| DFlash2，8 个草稿 token，Triton 草稿注意力 | **20.50** | 44.95 | **55.92** |
| DFlash2，8 个草稿 token，FA4 草稿注意力 | 18.39 | **45.29** | 54.58 |

最终保留了使用 Triton 的 DFlash2：长代码吞吐量约为无推测解码基线的 4.3 倍。
在没有后台编译的情况下复现了约 56 tokens/s 的结果。外部文章所称的
125–133 tokens/s 在这些工作负载和设置下**未能**复现。

## 保留的实验配置

容器使用 NVIDIA CDI（`--device=nvidia.com/gpu=all`）、8 GiB 共享内存，
API 端口仅监听环回地址。目标模型和草稿模型从上述版本的本地快照加载。
NixOS 主机启用了 Docker 和 NVIDIA 容器工具包；模型服务仍属实验性质，
没有声明式服务或自动启动机制。

通用服务器设置：

```text
--context-length 4096 --max-running-requests 1 --max-total-tokens 8192
--mem-fraction-static 0.65 --chunked-prefill-size 1024
--attention-backend triton --linear-attn-backend triton
--kv-cache-dtype bfloat16 --fp4-gemm-backend flashinfer_cutlass
--mamba-ssm-dtype bfloat16 --max-mamba-cache-size 8
--cuda-graph-backend-decode full --cuda-graph-max-bs-decode 1
--cuda-graph-backend-prefill disabled
--reasoning-parser qwen3
```

DFlash2 通过 `--speculative-draft-model-path` 添加固定版本的草稿模型快照，并增加：

```text
--speculative-algorithm DFLASH --speculative-num-draft-tokens 8
--speculative-draft-model-quantization unquant
--mamba-radix-cache-strategy extra_buffer
```

FA4 对比组增加 `--speculative-draft-attention-backend fa4`。无推测解码基线
省略推测解码参数；MTP 则使用
`--speculative-algorithm EAGLE --speculative-num-steps 3
--speculative-eagle-topk 1 --speculative-num-draft-tokens 4`，并使用目标模型的
MTP 权重。这两组保留默认的 Mamba radix-cache 策略。

探索性运行得到的兼容性结论如下，不作为额外的复测排名：

- 全模型 FA4 在 `head_dim=256` 的可变序列接口上失败。
  仅用于 DFlash2 草稿模型的 FA4 能够成功启动，并已在上文复测。
- 使用 `torch.compile` 的 DFlash2 在启动/图捕获期间失败，因此未计入结果。
  不使用该标志时，解码 CUDA Graph 仍保持启用。
- 针对已安装的驱动选择了较旧且固定的 CUDA 13.0.3 镜像；
  较新的 CUDA 13.4 镜像未经验证。

## 原始模型草稿头 INT8 后续试验

2026-09-13，使用相同的原始检查点、DFlash2 草稿模型、固定版本的 SGLang
运行时和三项工作负载协议，复现了 20.510 / 44.993 / 55.966 tokens/s。
九次实测的回复文本均与此前的原始模型基线一致。本次后续试验没有把 Huihui
测量值复用为原始模型结果。

每份原始模型跟踪都包含十一次草稿 Graph 重放和十一次目标 Graph 重放。
两种图都包含一次形状为 `[248320,5120]` 的完整 BF16 词表投影，草稿模型中约为
9.78 ms，目标模型中约为 9.73 ms。原始目标 Graph 耗时约 81–83 ms，而较早的
Huihui 跟踪约为 70–71 ms。两种目标模型的精度组合不同：原始跟踪包含 128 次
FP8 GEMM 及相应的 FP8 激活量化，而 Huihui 跟踪多出 128 次 NVFP4 GEMM。
不要仅因两个检查点都带有 NVFP4 标签，就将其视为相同内核的运行时对比；
精确的模块映射仍需直接的形状证据。

### 保留 DFlash2 选择器

实际捕获路径是 `sglang/srt/models/dflash.py` 中的 `_SelectorDraftSampler` →
`_selector_lattice` → `DFlash2DraftModel.compute_candidates`。
它先投影完整词表，再应用 radix top-k、一元 logit 变换和学习得到的选择器。
普通的 `_DflashDraftSampler` matmul 属于另一条路径。最初的集成保护在服务启动前
拒绝了该选择器配置，因此恢复了 BF16 服务；这是集成错误，并非 INT8 数值探测失败。

修正后的实验仅替换 `compute_candidates` 内、现有 top-k 之前的 TP1 全词表投影。
Graph 和 eager 执行均保留选择器及目标验证。在捕获草稿 Graph 前构建独立的逐行
INT8 权重副本；激活值使用动态逐行 INT8 缩放、INT32 累加和 BF16 输出。
对于整数 GEMM，较少的行数会填充到 32。全部 248320 个词表项仍然可用。
共享目标头保持 BF16；草稿副本会增加约 1.184 GiB，而不是缩减目标模型内存。

真实检查点的模型头通过了 M7/M8 检查：对照对象为同一量化方式的独立 FP64
整数点积实现；此外也通过了空输入/零输入及缓冲区变化的 CUDA Graph 检查。
计入激活量化和重新缩放后，独立 Graph 的中位数在 M7 时为
9.787 → 5.043 ms，在 M8 时为 9.790 → 5.104 ms。这些初始输入是合成数据。

### 服务结果与真实隐藏状态

三次运行的流式基准测试期间禁用了采样：

| 工作负载 | BF16 草稿头 | INT8 草稿头 | 变化 | 回复文本 |
| --- | ---: | ---: | ---: | --- |
| 中文 | 20.510 TPS | 20.670 TPS | +0.8% | 有变化 |
| 短代码 | 44.993 TPS | 46.934 TPS | +4.3% | 相同 |
| 长代码 | 55.966 TPS | 57.682 TPS | +3.1% | 有变化 |

每项 INT8 工作负载在三次实测重复中均保持稳定。单独的原生 `/generate` 请求
使用相同的聊天模板 token ID，其输出与对应的流式输出一致。逐请求推测计数器报告的
接受率分别为：中文 17.67% → 16.71%，短代码 57.69% → 57.69%，长代码
74.81% → 73.31%。这些是单请求计数器对比，并非服务器日志窗口或累计平均值。
相应的接受长度分别为 2.246 → 2.169、4.923 → 4.923 和 6.206 → 6.132。
提议计数可能超出请求的输出上限。中文和长代码的生成轨迹发生了变化，因此无法将
它们的全部吞吐量差异都归因于更快的投影。

| Graph GPU 时间跨度中位数 | 中文 BF16 → INT8 | 长代码 BF16 → INT8 |
| --- | ---: | ---: |
| 草稿 | 23.366 → 18.825 ms | 23.622 → 19.145 ms |
| 目标验证 | 80.885 → 80.842 ms | 82.705 → 82.796 ms |

每次重放中的全部 1066 个目标内核都保持相同的名称、网格和数量。
草稿模型中的另外 131 个内核没有变化：一个 BF16 头被整数 GEMM 及量化/重新缩放
替代，共涉及 16 个内核。因此可以直接看到草稿模型耗时减少约 4.5 ms，而目标模型
耗时大致不变。内核耗时总和不等于独占墙钟时间或服务吞吐量。

随后通过默认关闭的采样功能，从 INT8 服务中采集了 16 个中文步骤和 16 个短代码步骤，
每步包含七行真实隐藏状态。使用相同的确定性 radix top-k 重新计算时，全部 32 个已保存
样本都精确复现了选择器之前的候选 ID 和 logit。BF16 与 INT8 模型头的 argmax 在
3/112 个中文行和 1/112 个代码行上不同。选择器的最终 token 通常并非模型头 argmax，
因此没有将其作为该项参照。这些是 INT8 轨迹样本，并非成对的 BF16/INT8 生成轨迹，
也不是广泛的质量证明。

一个 2823-token 的检索提示词通过了三次测试，其中包括前缀复用。JSON 正确；
生成的完整质数判断函数与 BF16 回复完全一致，而后者已通过自身的五项断言，以及对
-32 至 10000 范围内整数的 10033 次独立筛法检查。吞吐量测试中的代码回复仍受上限
截断，不能视为完整程序质量测试。

保留了 INT8 实验服务，并关闭性能分析和隐藏状态采样；健康检查返回 200，主机可用
内存约为 83 GiB。原始 BF16 容器和 Flash Next 启动配置仍可用于回滚。最明确的
实测收益是在文本及接受率相同的情况下提升短代码吞吐量。下一步是在保留原始目标模型
当前权重和精度的同时，检查其 FP8 投影形状与内核选择。原始脚本、跟踪及隐藏状态
样本仍保留在 Git 之外。

## 原始目标模型 FP8 后端探测（2026-09-13）

保留的 INT8 草稿服务在每次目标重放的 128 次 FP8 注意力投影上耗时
27.985 ms（中文）/ 30.107 ms（长代码）。通过检查点和运行时分析，
将其映射到以下合并权重形状：

| 投影 | 每次重放的调用次数 | 权重形状 `[N, K]` | 中文/长代码内核耗时总和 |
| --- | ---: | --- | ---: |
| GDN QKV/Z 输入 | 48 | `[16384, 5120]` | 15.204 / 15.347 ms |
| 注意力输出 | 64 | `[5120, 6144]` | 8.353 / 10.310 ms |
| 全注意力 QKV | 16 | `[14336, 5120]` | 4.428 / 4.450 ms |

128 次静态 FP8 激活量化额外增加约 0.277 ms。当前 GEMM 在 SM110 上使用
CUTLASS SM100 系列内核，操作数为 FP8 E4M3。探测加载了具有代表性的真实第 0/3 层
权重，复现了 SGLang 合并分片时的最大尺度再量化，并保持相同的静态激活量化。
输入为合成的 BF16 隐藏状态。

M8 下 CUDA Graph GEMM 的中位数，以毫秒计（五批，每批重放 50 次）：

| 后端 | QKV/Z | 输出 | QKV |
| --- | ---: | ---: | ---: |
| 当前 SGLang CUTLASS | 0.316970 | 0.117955 | 0.277806 |
| Torch 缩放矩阵乘 | 0.316388 | 0.120396 | 0.280870 |
| Torch 缩放矩阵乘，快速累加 | 0.317197 | 0.119820 | 0.280940 |
| FlashInfer cuBLAS | 0.342858 | 0.119924 | 0.280975 |
| FlashInfer CUTLASS | 0.318436 | 0.117555 | 0.277946 |

也测量了 M1；其中没有任何替代方案优于当前基线。M8 下最佳替代方案的纯 GEMM
差异低于 0.4%。在计入激活量化和相同的 FP8 复制后，一批输出投影中，基线耗时
0.121337 ms，FlashInfer CUTLASS 耗时 0.115972 ms（4.4%）。后者甚至低于其
单独测得的纯 GEMM 时间，说明这些连续批次容易受缓存状态和计时波动影响。
重复的单层重放也不同于完整模型。这项孤立结果不足以证明端到端收益，也不足以支持
更改服务。

在三种形状、M1/M8 以及随机/变化/零输入的组合中，FlashInfer CUTLASS 在全部
18 个案例中都与当前输出逐位一致。Torch 和 cuBLAS 各有 11/18 一致；所有输出均为
有限值，最大绝对差分别为 0.0078125 和 0.015625。这只是有限的数值检查，
不是模型质量评估。全部 120 项输入变化的 CUDA Graph 检查都与各自后端的 eager
输出逐位一致，包括零输入及从零输入恢复。三个基线探测内核的名称和网格与服务跟踪
完全一致。探测期间 PyTorch 峰值分配低于 351 MiB，峰值预留内存低于 395 MiB；
这些数值不包括正在运行的服务器和非 PyTorch 分配。

没有采用任何新后端，也不声称服务吞吐量有所提升。原始目标权重和 INT8 草稿服务
保持不变。原始脚本、结果和跟踪保留在 Git 之外。下一项有价值的实验是测量该原始
检查点上的 GDN 注意力状态/内核开销；实测结果不支持再为这些 FP8 GEMM 包一层封装。

## 原始目标模型 GDN 分块实验（2026-09-13）

上述 INT8 草稿跟踪显示，每次目标重放中有 4.234 ms（中文）/ 3.691 ms（长代码）
用于 GDN 循环更新、卷积、QKV/Z 拆分和门控归一化。仅循环更新一项在 48 次调用中
就占 3.238 / 2.667 ms，网格为 `[1, 4, 48]`。在图之外，SSM 状态和卷积窗口
scatter 每轮验证额外增加约 0.738 ms。这些内核耗时总和不等于独占墙钟时间。

在此配置下，DFlash 每轮验证八个有效 token。接受数量会在验证后选择一个已保存状态，
但不会缩短循环。SSM 验证保持其源状态不变，并在每一步保存 BF16 状态快照。
卷积验证具有不同的写回行为，其已接受窗口会在提交期间恢复。

已安装 FlashInfer 后端的验证保护排除了 SM110，而 CuteDSL 后端没有目标验证实现。
因此，本实验没有切换后端，而是在保持三个阶段的情况下，遍历现有 Triton 内核的
value 块大小（16/32/64）和 warp 数（1/2/4）。只有单 warp 配置通过了全部逐位检查；
更多 warp 会改变数值结果，因此被排除。

探测使用合成的紧凑 Q/K/V，模型配置为 16 个 key 头、48 个 value 头以及 128 维的
key/value 头，并使用非零 BF16 初始状态。检查项包括每 token 快照、保持不变的源状态、
非零池索引、未被触碰的填充区，以及大于运行时 token 数的已分配快照步幅。
输入变化的 CUDA Graph 检查还将输出和快照与原始内核进行了对比。

第二次探测固定输入，并在十批、每批 100 次 Graph 重放中交替基线与候选方案的顺序：

| 有效 token | 原始 BV32，单 warp | BV16，单 warp | 内核降幅 |
| --- | ---: | ---: | ---: |
| 1 | 0.012309 ms | 0.010264 ms | 16.6% |
| 3 | 0.023340 ms | 0.018680 ms | 20.0% |
| 8 | 0.056102 ms | 0.041098 ms | 26.7% |

三项固定输入对比均逐位相等。候选补丁需显式启用，且仅限于 SM110、批大小为一、
原始八 token 验证形状、BF16 状态和输入，以及现有的非 tree/非 KDA/非 ring 路径。
它只更改 BV；算术、warp 数和状态提交均保持不变。这些独立检查不能取代服务级验证。

### 服务 A/B 测试

新的基线复现了此前 INT8 服务的文本和吞吐量。随后对相同的三项工作负载分别进行
一次短暂预热和三次实测重复，得到：

| 工作负载 | 原始 BV32 | 候选 BV16 | 变化 |
| --- | ---: | ---: | ---: |
| 中文 | 20.671 TPS | 20.792 TPS | +0.59% |
| 短代码 | 46.930 TPS | 47.206 TPS | +0.59% |
| 长代码 | 57.681 TPS | 58.023 TPS | +0.59% |

九次实测的回复文本和 token 用量均完全相同。在这三次重复中，候选方案与基线的
吞吐量范围没有重叠；但这仍是小规模固定工作负载实验，不代表广泛的性能结论。

| 性能分析指标 | 中文 BV32 → BV16 | 长代码 BV32 → BV16 |
| --- | ---: | ---: |
| 每次目标重放的循环内核耗时总和 | 3.238 → 2.652 ms | 2.667 → 2.073 ms |
| 目标 Graph 时间跨度中位数 | 80.842 → 80.253 ms | 82.796 → 82.107 ms |
| 草稿 Graph 时间跨度中位数 | 18.825 → 18.813 ms | 19.145 → 19.115 ms |

每份跟踪都包含 11 次草稿/目标重放。目标内核网格唯一的变化是 48 次循环调用，
从 `[1, 4, 48]` 变为 `[1, 8, 48]`。其他所有目标内核的名称、网格和数量均未改变，
所有草稿内核也没有变化。两项工作负载中都能看到循环耗时减少约 0.59 ms；
全模型收益小于独立测试中的 27%。

五个原生请求（三项工作负载、JSON 和一个完整质数判断函数）保持了相同文本及全部
逐请求推测计数器。中文/短代码/长代码的接受率仍为
16.71% / 57.69% / 73.31%。功能性回复与先前验证过的程序完全一致；
受上限截断的吞吐量回复仍不能视为完整程序质量测试。一个 2823-token 的检索提示词
通过了三次测试，其中包括前缀复用。

完成这些检查后，实验服务选择了 BV16 配置。重启后，检索测试又通过三次，健康检查
返回 200，隐藏状态采样仍关闭，内存看门狗保持活动。原始 INT8 草稿/BV32 容器仍可
用于回滚。这是约 0.6% 的服务改进，而非独立内核的 27%。原始探测程序、补丁生成器、
启动/回滚脚本和跟踪保留在 Git 之外。后续工作应优先处理实测开销更大的部分，
例如目标 LM 头，同时保持目标模型精度并验证生成输出。

## 原始目标模型 BF16 头后端探测（2026-09-13）

保留的 GDN-BV16 服务在每次验证重放的全词表目标头上耗时 9.812 ms。实际入口为
`torch.matmul`，输入是 BF16 隐藏状态和转置后的 BF16 权重；它先生成 BF16 logit，
再复制到 FP32 采样缓冲区。验证会投影全部八行。直接输出 FP32 的 GEMM 会绕过这个
BF16 舍入步骤，因此未被视为等价替代方案。

真实的 `[248320, 5120]` 模型头包含 2542796800 字节（2.368 GiB）。用该大小除以
服务耗时得到约 259 GB/s；这是权重字节数与时间之比，并非实测内存带宽上限。
独立探测检查了完整词表并记录原始权重 SHA256，同时使用合成 BF16 隐藏状态。
它保留现有的低精度归约设置，并未量化模型头。

计时期间所有后端共享固定输入。五批、每批 20 次 CUDA Graph 重放交替使用正向/反向
后端顺序。以下为 GEMM 中位数，不含后续的 FP32 复制：

| 后端 | M8 | M1 |
| --- | ---: | ---: |
| 当前 Torch matmul | 9.7837 ms | 9.8691 ms |
| Torch F.linear | 9.7457 ms | 9.8404 ms |
| Torch addmm，beta=0 | 9.7515 ms | 9.8251 ms |
| 65536 大小的词表分块并拼接 | 9.8734 ms | 9.9349 ms |
| FlashInfer cuBLASLt | 9.7672 ms | 9.8292 ms |
| FlashInfer cuDNN | 9.7769 ms | 9.8669 ms |
| FlashInfer TinyGEMM | 9.4113 ms | 9.4230 ms |

基线、F.linear、addmm、cuBLASLt 和 cuDNN 在每个 M 下都调度了名称和网格相同的
内核。在 M8 下，它们与服务跟踪中的
`nvjet_sm110_tst_128x8_64x12_2x1_v_bz_TNT` 完全一致，网格为
`[1940, 1, 1]`。每个后端在全部八种随机/变化/零输入/恢复案例中的输出均逐位一致。
当捕获到的 GPU 工作相同时，不足 0.5% 的计时差异不足以证明更换后端有实际价值。

全部 56 项输入变化的 Graph 检查都与各自后端的 eager 输出一致，结果均为有限值，
并在这些合成输入上保持了基线 argmax。尽管如此，TinyGEMM 和词表分块各自在全部
六个非零案例中都与基线 logit 不同，最大绝对差为 0.03125。两者最差的差异元素占比
分别为 0.234% 和 0.122%。TinyGEMM 在 M8 下提升约 3.8%（0.372 ms），但合成输入
上的 argmax 不变，并不能证明在真实隐藏状态上有等价的目标接受率或采样结果。
没有为其进行服务 A/B 测试，也未声称模型质量等价。

没有采用任何模型头后端。现有 INT8 草稿/GDN-BV16 服务保持健康，内存看门狗处于
活动状态，隐藏状态采样关闭。探测期间 PyTorch 峰值分配/预留为
2.506/2.627 GiB，不包括服务器和非 PyTorch 分配。原始脚本、校验和、数值结果及
内核跟踪保留在 Git 之外。下一个实测开销更大的目标部分是两组 NVFP4 投影，
每次重放约 37 ms；应先检查其实际形状和 tactic，再提出下一项服务变更。

## 原始目标模型 NVFP4 tactic 探测（2026-09-13）

保留服务中的 128 次 NVFP4 GEMM 由 64 次合并的 gate/up 投影和 64 次 down 投影组成。

| Gate/up | `[34816, 5120]` | `[34816, 2560]` | `[2, 272, 1]` | 0.3812 ms |
| Down | `[5120, 17408]` | `[5120, 8704]` | `[1, 40, 1]` | 0.1965 ms |

完整的 M8 遍历涵盖 32 个显式 CUTLASS tactic，以及每种形状的无缓存封装器和原始

tactic：gate/up 为 4，down 为 21；保存的服务自动调优缓存也独立确认了两个 ID。
这些 ID 仅适用于已安装的 FlashInfer 构建和这些形状。

## DFlash 块大小对比（2026-09-13）

本实验将块大小 4 和 16 与保留的块大小 8 服务进行对比。一个块包含一个锚点 token，
因此大小 4/8/16 分别最多提出 3/7/15 个草稿 token。草稿检查点声明的块大小为 8；
已安装的运行时允许覆盖，并会同步草稿卷积边界、掩码/位置缓冲区及选择器长度。
运行时支持并不能证明被覆盖的大小具有训练或质量覆盖。

草稿注意力是非因果的，因此块大小 4 并非简单截取块大小 8 的前三项提议。验证/提交
边界的变化也可能影响 BF16 计算。跨大小的回复一致性经过实测，并非预先假定。
该对比保留现有 GDN 保护：块大小 8 使用已验证的 BV16 优化，块大小 4 和 16 使用
原始 BV32。因此对比的是实际部署配置，而非单独隔离块大小这一变量。

首次以块大小 4 启动时，被实验性隐藏状态捕获的启动保护拒绝。仅删除采样触发文件仍不够：
设置其捕获目录环境变量依然会构建只支持块大小 8 的诊断对象。重试时完全省略捕获目录和
限制变量，同时保持独立的 INT8 模型头开关启用。没有削弱任何保护。失败的启动日志和
回滚记录均已保留。

新的块大小 8 基线复现了保留服务的回复文本。每种配置对每项工作负载进行一次短暂预热
和三次实测重复，并使用相同的采样设置、提示词和输出上限：

| 工作负载 | 块大小 4 | 块大小 8 | 块大小 16 | 块大小 4/16 相对 8 的变化 |
| --- | ---: | ---: | ---: | ---: |
| 中文 | 19.272 TPS | 20.742 TPS | 19.474 TPS | -7.1% / -6.1% |
| 短代码 | 35.289 TPS | 47.094 TPS | 72.454 TPS | -25.1% / +53.9% |
| 长代码 | 35.145 TPS | 57.883 TPS | 74.560 TPS | -39.3% / +28.8% |

每种配置在各自三次重复中的文本都保持稳定，但块大小 8 与每个替代方案之间的九项
实测回复全部发生变化。token 用量保持相同。这些是观测到的工作负载差异，
不是相同文本条件下的加速，也不是孤立的算术节省。

使用相同 token 化提示词的原生请求报告了以下逐请求计数器
（块大小 8 / 块大小 4 / 块大小 16）：

| 工作负载 | 草稿接受率 | 每轮接受长度 | 验证轮数 |
| --- | --- | --- | --- |
| 中文 | 16.71% / 32.31% / 7.62% | 2.169 / 1.969 / 2.151 | 118 / 130 / 119 |
| 短代码 | 57.69% / 87.32% / 47.50% | 4.923 / 3.606 / 8.000 | 52 / 71 / 32 |
| 长代码 | 73.31% / 88.02% / 48.78% | 6.132 / 3.644 / 8.325 | 167 / 281 / 123 |

仅看更高的接受百分比会产生误导：块大小 4 每轮接受的 token 更少，需要更多验证轮次。
块大小 16 虽然接受率更低，却大幅减少了代码验证轮数。这些计数器属于实际观测到的
不同输出轨迹；提议计数可能超出请求的输出上限。

每项工作负载的跟踪包含 11 次草稿/目标重放。以下目标/草稿 Graph 中位数以毫秒计，
并使用保留的块大小 8 参考跟踪：

| 工作负载 | 块大小 8 目标/草稿 | 块大小 4 目标/草稿 | 块大小 16 目标/草稿 |
| --- | --- | --- | --- |
| 中文 | 80.253 / 18.813 | 79.023 / 18.809 | 85.939 / 19.027 |
| 长代码 | 82.107 / 19.115 | 80.150 / 19.003 | 87.922 / 19.260 |

块大小 4 并未将每轮开销减半。它仍会运行全部模型投影，而且 INT8 草稿头会将三行和
七行输入都填充到 M32。块大小 16 每轮验证开销更高，但其代码工作负载能接受足够多的
额外 token，从而提高吞吐量。这解释了测量结果的变化方向，同时没有把全部差异归因于
某一个内核。

两个替代方案都三次通过了 2823-token 检索测试，其中包括前缀复用。JSON 仍然正确。
块大小 4 的完整质数判断回复与先前验证过的程序一致。块大小 16 生成了另一个完整程序，
通过了自身生成的五项断言，以及在 -32 至 10000 范围内与独立筛法进行的对比
（10033 次检查）。受上限截断的吞吐量回复未被视为完整程序质量测试。

实验服务最终选择了块大小 16，优先考虑实测代码吞吐量，同时接受中文约 6% 的降速。
INT8 草稿投影保持启用；窄范围的 GDN-BV16 优化在块大小 16 下不启用，后者使用原始
BV32。已验证的块大小 8 容器仍可用于回滚。原始启动器、失败日志、基准回复、
性能分析和检查保留在 Git 之外。性能调优暂时停止；下一优先事项是通过共享 LiteLLM
入口提供持久化的 OpenAI 兼容服务。进一步调优将等待基础设施稳定和运维交接。

## 原生 256K 容量测试——2026-09-14

临时启用了上述候选配置：上下文 262144，实际 token 池 270336，BF16 KV，
分块预填充 1024，内存比例 0.65，DFlash2 块大小 16 并使用 INT8 草稿头，

### 集成内存预算修正

随后的一次共存尝试甚至在加载无草稿权重之前就失败了：CUDA 报告可用空间为
10.69 GiB，而 Linux 报告 `MemAvailable` 为 56.65 GiB（包括可回收内存）。
NInfer 的权重准入和后续 KV 规划都使用 `cudaMemGetInfo`。当 CUDA 识别到集成 GPU 时，
SGLang 已经改用主机可用内存。NVIDIA 也
[记录了这一 Tegra 内存估算限制](https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/)。

修正将这些检查集中到 `DeviceContext::available_memory()`。在 Linux 集成 GPU 上，
它使用 `MemAvailable`，并以 CUDA/设备总内存为上限；主机数据缺失或格式错误时，
回退到 CUDA 可用空间。独立 GPU 的行为不变。不计入 swap，也不会绕过分配失败或 KV
余量检查。这修正的是准入估算；不会减少分配，也不会为避免其他进程竞争而预留内存。

[源码补丁](../../engine/patches/ninfer-linux-integrated-memory.patch)可在 Pi SM110 工作树根目录
使用 `patch -p1` 应用。其原始上游归档 SHA256 为
`7d5b943fac1f88363da72d3e7f39b6a15d3261f2d0f73d2880a1385f88529056`;
该归档不是 Git 检出。此补丁只包含内存修正，不包含较早的 SM110 移植或完整的
NVFP4 实现。

新的 CPU 测试覆盖解析、缺失/不可读/格式错误的数据、溢出、零可用空间、容量上限和
独立 GPU 行为，并已通过。随后完整 CLI 面向 `110a` 成功重新构建。

修正后，在已部署 SGLang 服务始终驻留的情况下，相同的九项案例再次通过，其中包括
DFlash2。主机采样器每 0.5 秒采样一次，共记录 173 个样本：Available 最低为
35.71 GiB，Free 最低为 8.20 GiB（两者是各自的最低值，不保证是瞬时峰值）。
运行期间，通过生产 OpenAI 网关发起的两个短请求也返回 HTTP 200 和预期输出，
分别耗时 0.539 和 0.645 秒。生产服务的调用配置保持不变，自动重启次数为零。
清理过程停止实验容器后，另一个请求在 0.318 秒内通过。

这验证了短 4K NInfer/SGLang 共存。但它没有证明在四个并发的生产长请求、较长的
NInfer 上下文或持续 agent 工作负载下仍有足够余量。没有更改持久化服务参数。
进行隔离性能测试时，应使用上述独立恢复任务停止另一个模型服务器。

### 独占引擎对比与 NVFP4 后续试验

在这次独占 GPU 试验中，每个被测引擎都单独运行。一个独立且有时限的 systemd 任务
负责停止/恢复生产服务。现有 SGLang 基线保留四请求/256K 配置、BF16 KV、
ModelOpt NVFP4/FP8 权重和 BF16 输出头。NInfer 使用四请求/32K 配置及共享的
64K FP8 KV 池。这些是端到端配置对比，不是等量化内核基准，也不代表质量等价。

所有请求使用相同提示词、零温度、零 presence/frequency penalty、禁用思考、SSE 和
512 个输出 token。提示词计数一致：计数任务为 43，代码生成为 82，较长预填充案例为
1843。每个计时请求/组之前都会清空 SGLang 的前缀缓存；NInfer 禁用前缀复用。
计数任务要求输出 1 至 2000 的整数；代码任务要求编写带重试、截止时间、持久化和测试的
异步 Python 作业队列。输出被刻意设置为触及长度上限：代码吞吐量不能证明完整实现正确。

单请求速率为 `(completion_tokens - 1) / (last_stream_time -
first_content_time)`，取三次计数运行和两次代码运行的中位数。四请求聚合速率包含全部
四个请求的预填充与解码墙钟时间。这两类速率的分母不同，不应混用。计数任务高度可预测，
有利于推测解码。

| 配置 | 计数解码 tok/s | 代码解码 tok/s | 四请求计数聚合 tok/s |
| --- | ---: | ---: | ---: |
| SGLang，DFlash 块大小 16 | 119.44 | 66.47 | 331.51 |
| NInfer groupwise-int，无草稿 | 10.45 | 10.45 | 24.38 |
| NInfer groupwise-int，DFlash2 draft7 | 31.31 | 22.79 | 74.57 |
| NInfer groupwise-int，DFlash2 draft15 | 41.85 | 19.06 | 105.47 |
| NInfer 混合 NVFP4，A16，无草稿 | 10.47 | 10.47 | 30.77 |
| NInfer 混合 NVFP4，A16，DFlash2 draft15 | 46.60 | 20.78 | 53.37 |
| NInfer 混合 NVFP4，A16，DFlash2 draft7 | — | 25.51 | — |

NVFP4 draft7 补充测试只测量了两个代码请求。相较 groupwise draft7，其代码速率提升约
11.9%，但在该工作负载上，SGLang 的解码速率仍约为其 2.6 倍。NVFP4 draft15 虽然
单请求计数更快，但在四请求工作负载中出现倒退。本次试验中没有任何一种 NInfer 配置
优于已部署的 SGLang 基线。

对于 1843-token 输入，客户端 TTFT 分别为：SGLang 0.679 s、无草稿 NInfer groupwise
6.093 s、无草稿 NVFP4 A16 24.997 s；NVFP4 draft15 仍耗时 25.051 s。
推测解码无法消除这部分预填充开销。所有计时输出都达到了请求的 512-token 上限。
因此该实验仍只是移植/验证候选方案，不是生产升级。

增大 groupwise 草稿窗口有助于计数，却损害了该代码工作负载。SGLang 的块大小 16
对应 NInfer 中由 15 个草稿 token 加一个锚点组成的块；保留 draft7 结果是为了展示
该参数的敏感性。

[完整 SM110 源码补丁](../../engine/patches/ninfer-sm110-complete.patch)包含原始架构保护/桩、
集成内存修正，以及 NVFP4 的 A16 功能路径。它可应用于上述 SHA256 所标识的原始上游
归档，无需未归档的 Pi 工作树。已检查将其应用到全新源码的结果，并逐字节复现了源码
快照。规划与执行会一致地选择 A16 策略；NVFP4 SwiGLU 现在以不超过 16 token 的分块
处理较长输入。真正的原生 W4A4 实现仍未移植。

五项设备测试通过：NVFP4 A16 Linear、NVFP4 Linear+Residual、NVFP4 SwiGLU、
FP8 A16 Linear 和 FP8 A8 Linear。Linear 检查在真实形状下使用采样的独立 FP64
参考实现。SwiGLU 使用稠密首 token 和稀疏后续 token 输入检查所有输出行，包括
T=17/31/32/33/256/257 和 Graph 重放。第一项边界测试暴露出错误复用通用 32-token
限制的问题；现在由共享的 SwiGLU 专用 16-token 限制同时控制分区及其启动器表。
预言机案例和容差均予以保留。

随后，匹配的 NVFP4 制品在 eager、Graph 和 DFlash2 模式下通过了相同的九项短 JSON、
检索和算术案例。这些检查证明了所测 A16 路径可以正常执行，并不代表广泛的模型质量
或原生 W4A4 验证。

匹配的已发布制品为
[neroued/Qwen3.8-27B-nvfp4-NInfer](https://huggingface.co/neroued/Qwen3.8-27B-nvfp4-NInfer)，
版本 `11dbbbbbc33db198afe2f02c9232c771ff7031be`，大小 23719496192 字节，
SHA256 `552c374c685dce302603b95fbe940fb04243c0cd44c083efc644ad3d980d462c`。
它使用作者的混合 FP8/NVFP4 方案，包括 FP8 输出头；并非已部署的 ModelOpt/BF16 头
检查点。后者的张量/尺度布局不同，不能直接交给该方案处理。

对于后续原生内核工作，NInfer 当前 warp 级的 `mma.sync.aligned.kind::mxf4nvf4`
路径不同于 SM100/SM110 的 `tcgen05.mma` 路径；后者使用 Tensor Memory，并采用不同的
CTA/同步契约。参见 [NVIDIA PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/#warp-level-matrix-instructions-mma)。
已安装 FlashInfer 的 `mm_fp4` Cutlass 调度器接受 SM 主版本 10/11，并选择
`fp4_gemm_template_sm100.h`；内置的 CUTLASS `mma_sm100_umma.hpp` 包含真正的块缩放
`tcgen05.mma` 指令。下一个明确的移植目标是 MLP down GEMM `[5120,17408]`，
随后进行残差相加。复用前必须以独立预言机验证紧凑编码、K16 尺度布局和全局尺度；
相似的布局名称不能证明字节兼容。A16 结果并不代表原生 NVFP4 硬件性能上限。

### 原生 SM110 MLP down 试验

后续独占试验使用 SM110 的原生块缩放 Tensor Core 路径，从 MLP down
`[N=5120,K=17408]` 开始。参考实现为 FlashInfer 0.6.17
（`a0a6b019b9b27d49d209f85d028a1ae5a9b347d7`）的
`fp4_gemm_template_sm100.h` 及其内置 CUTLASS。独立 C++/CUDA 探测程序实例化一个
使用 1 个 SM 的 `128×128×256` tile，cluster 为 `1×1×1`，输出为 BF16，累加为 FP32。
它在 Thor SM110a、CUDA 13.0 和驱动 13.2 上运行；不会调用 Python 推理。

紧凑权重字节和 `blockscale-k16-m128x4-v1` 尺度直接匹配 CUTLASS 的 SFB 布局。
每个逻辑权重坐标都与独立编写的偏移公式进行了核对。无需第二份权重副本或运行时重新
打包。激活尺度不同于 NInfer 的 SM120 布局：SFA 必须使用相同的交错方式，且行范围
需填充到 128。K=17408 时，尺度平面需要 `ceil(T/128)*128*1088` 字节。

预打包输入探测在 T=1,8,16,17,32,64,127,129,256,1024 下通过了独立 FP64 采样 GEMM
预言机和完整输出有限值检查。它使用有符号 E2M1 编码、非均匀 E4M3 尺度和全局
alpha=0.75。这验证了紧凑算术和最终 BF16 舍入；并未证明 BF16 激活量化精度或模型质量。

经过 10 次预热和 30 次采样，驱逐 256 MiB 缓存后的 CUDA event 时间中位数为：

| Token 数 T | A16 纯 Linear，ms | 原生预打包 GEMM，ms |
|---|---:|---:|
| 1 | 0.303 | 0.214 |
| 8 | 0.639 | 0.216 |
| 16 | 1.144 | 0.267 |
| 32 | 2.179 | 0.267 |
| 64 | 4.357 | 0.269 |
| 256 | 17.402 | 0.277 |
| 1024 | 69.603 | 0.585 |

两列都不含残差相加；原生路径还不含 BF16 至 NVFP4 激活量化。这些是内核级的潜在收益，
不是端到端模型加速。A16 基准内置的 RTX 5090 带宽百分比不适用于 Thor，此处没有使用。


完整移植通过显式的 `NINFER_CUTLASS_INCLUDE_DIR` 构建选项，为 `AllowA4` 和 T≥8 启用
原生 `[5120,17408]` LinearAdd。只有 27B MLP down 执行策略和与之匹配的工作区规划器
会选择该路径。Gate/up 和其他 NVFP4 运算保留此前的 SM110 A16 行为。原生路径复用
现有 K16 激活编解码器，直接写入交错 SFA，初始化填充，并在最终 BF16 存储前融合残差
相加。所有临时存储都属于调用方的 arena；不存在运行时权重重新打包或隐藏的 GPU 分配。

扩展后的公开 LinearAdd 测试以独立解码的权重和用 FP64 表示的 BF16 输入为参照，
通过了未更改的 A4 误差标准。覆盖范围包括 T7/8/16/17/127/128/129/1024、精确大小的
工作区及保护区、使用变化的有符号输入进行 Graph 重放，以及零输入下精确保留残差。
首次测试夹具运行在到达原生内核前就拒绝了大小为零的借用 arena 存储；现在零工作区
A16 测试会提供 256 字节后备空间，同时仍要求分配峰值为零。原生路径保持精确报告的
工作区容量。

完整 LinearAdd（包括激活量化和残差）在 T8、T16、T256 和 T1024 下分别测得
0.283 ms、0.284 ms、0.318 ms 和 0.750 ms，使用 10 次预热和 30 个冷缓存 CUDA event
样本。此前的九项短模型案例也在 eager、CUDA Graph 和 DFlash2 模式下通过。
这些功能和数学检查不能证明广泛的模型质量等价。

[完整源码补丁](../../engine/patches/ninfer-sm110-complete.patch)包含该原生路径、目标策略、测试和
构建说明，并已针对原始源码 tar 重放。独立的预打包输入
[探测程序](../../engine/probes/ninfer-sm110-native/native-probe.cu)和
[编译命令](../../engine/probes/ninfer-sm110-native/compile.sh)分开归档；它们需要经验证的
FlashInfer 内置 CUTLASS 头文件。


端到端测量保留相同的匹配 NVFP4 制品、32K 上下文/64K 池、四请求容量、FP8 KV、
CUDA Graph、禁用前缀复用、贪心采样和 512-token 输出预算。只有 MLP down 发生变化。
代码速率是使用此前相同代码提示词运行两次所得的中位数；四次代码运行均输出
512 个 token，并以 `length` 结束。

| 测量项 | 先前的 A16 移植 | 原生 MLP down | 变化 |
|---|---:|---:|---:|
| 无草稿代码解码 | 10.47 tok/s | 10.46 tok/s | 基本不变 |
| DFlash2 draft7 代码解码 | 25.51 tok/s | 28.43 tok/s | +11.4% |
| 无草稿，1843-token 输入 TTFT | 25.00 s | 17.84 s | −28.6% |

原生 draft7 在该输入上的 TTFT 也测得 17.88 s；此前未测量 draft7 TTFT，因此不声称
存在对应的加速。此前 SGLang 代码结果仍为 66.47 tok/s，显著高于这项部分移植。
本次试验支持继续移植剩余的 MLP gate/up 路径；不足以支持替换日常 SGLang 服务。

随后，四个并发的显式 JSON 请求返回了完全符合预期的 95-token 对象；服务器统计显示
有四个正在运行、可解码的请求，批大小为 4。较早的一个短提示词返回了全部四项回复，
但其中三项把请求的数字用作 JSON 键；该失败夹具予以保留，不计为通过，也不作为模型
质量证据。显式夹具验证的是并发执行，而非吞吐量。机器可读的
[结果](../../engine/probes/ninfer-sm110-native/results.json)记录了成功的检查、测量及这些限制。
