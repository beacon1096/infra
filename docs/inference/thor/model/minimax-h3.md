# MiniMax H3：Lazycat 部署与基准测试

[Thor 概览](../../README.md)

检查与试验日期：2026-09-18。本文只读记录了在一台 Thor T5000 上安装的官方 Lazycat 软件包；
它不是上游 MiniMax H3 在其推荐服务栈上的基准测试。

测试的平台版本：

- AI Pod: `2.2.4-nightly.20260917081204+43444c8`
- Lazycat compute-capsule firmware (`算力舱固件`):
  `2.2.4-nightly.20260917081206+43444c8`
- Lazycat MiniMax H3 应用/LPK：`0.1.9`
- MiniMax H3 算力运行时：`runtime-160-0.1.1`

观察到的主机运行 Ubuntu 24.04.4、Jetson Linux R39.2、Linux 6.8.12-1021-tegra、
NVIDIA 驱动 595.78 和 CUDA 13.2，处于 120 W 功率模式。算力舱控制面板将风扇设为性能模式
（`风扇-性能模式`）。私有地址、设备主机名和标识符已省略。

## Lazycat 管理应用

对 Lazycat 微服务器上的原始软件包及其持久化部署记录进行只读检查，发现：

- 软件包 ID 为 `cloud.lazycat.aipod.minimax-h3`，版本为 `0.1.9`；
- 管理镜像为 `registry.lazycat.cloud/catdogai/minimax-h3-lpk:0.1.9-amd64-v1`，摘要为
  `sha256:8a536b135d4aa163d039c2a500adf0adcd800310a90ca54336462af5cf142137`;
- 原始 LPK SHA-256 为
  `2ab34fa7be421c80781855f28d25aab97bc1e68ca3dc9b28b50716d9f6ecc479`;
- 保存的模型 ID 为 `minimax-h3-video`，模型版本为 `0.1.9`，部署模式为 `custom`；
- 请求并允许的最大并发序列数均为一，保存的上下文长度值为 8，预估设备内存为 72 GiB。

保存的部署记录将算力镜像固定为 `registry.lazycat.cloud/catdogai/minimax-h3:runtime-160-0.1.1`，
并记录了热缓存产物 `minimax-h3-t5000-warm-cache.tar.gz`。管理应用报告，从开始环境检查到
模型 API 健康共耗时 291.03 秒；这个较宽的时间区间与下文运行时启动计时不同。

MiniMax H3 应用的部署页面没有可选部署选项。因此，上述保存的并发、上下文长度和内存字段
描述的是应用的固定/默认部署配置，而非此次测试所做的选择。

软件包清单和部署记录中均无独立的算力舱配置模式或发布版本号。因此，可复现的版本标识
由平台/固件构建版本、应用版本 `0.1.9`、运行时标签和镜像摘要共同组成，而不是一个统一的 H3 版本号。

## 打包的运行时

该软件包并非上游 MiniMax vLLM 或 SGLang 服务。Lazycat 代理启动一个 Docker Compose 服务，使用：

- 镜像 `registry.lazycat.cloud/catdogai/minimax-h3:runtime-160-0.1.1`；
- 镜像摘要
  `sha256:e37d78b4fdda01fa3e7cf82a6cd8dc7b14f4249bbfb12fa7eebe66db22b53ad4`;
- 镜像创建时间为 2026-09-11，本地镜像大小报告为 85.38 GB；
- 主机网络和 IPC、全部 NVIDIA GPU、`IPC_LOCK`、容器内 root 用户，以及 `unless-stopped` 重启策略；
- Hugging Face 和 Transformers 离线运行；
- 绑定挂载的编译器缓存和持久化输出目录。

管理代理在启动 H3 前停止了此前运行的模型服务。部署日志显示所有镜像均已在本地预加载。
容器在 Compose 启动约 285.8 秒后达到健康状态；模型自身的时间戳显示从进程启动到就绪耗时
279.18 秒。

镜像标签标明 OpenVDN `vdn-minimax-h3` 提交 `b8cb28f` 和经过补丁修改的 Diffusers 提交
`3a2f35d`。Lazycat 的修改说明指出，其 Thor 改动将连续窗口注意力查询的 gather/scatter 操作
替换为切片；其自身对三个配置的逐字节检查报告端到端性能提升 1.06% 至 1.86%。

运行时使用 Python 3.12.13、Torch 2.11.0、Diffusers `0.40.0.dev0`、Transformers 5.12.1、
Triton 3.6.0 和 FlashAttention 2.8.4。容器镜像继承了面向 vLLM 的基础镜像，
但 H3 服务本身是自定义 Python `ThreadingHTTPServer`，并非 vLLM。

## 模型组装

镜像的 VDN 工作目录内嵌约 78 GB 数据：

| 组件 | 约占空间 |
| --- | ---: |
| H3-Base transformer，14 个 safetensor 分片 | 62 GB |
| 视频 VAE，3 个分片 | 9.8 GB |
| Audio VAE | 578 MB |
| VDN 线性注意力分支 | 4.0 GB |
| 默认 LoRA | 319 MB |
| 八步 turbo LoRA | 813 MB |
| 三个预编码提示词 | 29 MB |

启动时，它在 H3-Base 基础上组装 `stage-dmd-step-250` VDN 检查点，加载 800 个分支张量并合并
571 对 LoRA。推理固定为八次模型求值，设置 `video_shift=12.0` 和 `audio_shift=3.0`，
在 Thor 上选择分解式 window-softmax 路径，并将 363 个宽 Linear 模块转换为 FP8 E4M3。
服务警告 FP8 会改变生成样本，因此即使使用相同种子也无法复现 BF16 渲染结果。

这与完整的上游 H3 系统不同。所检查的软件包仅包含文本生成音视频的 VDN 路径；
它未提供首帧/末帧、参考图像、视频或音频输入。

## API 与功能限制

服务直接监听主机网络端口。其 API 提供健康检查、模型、能力、异步生成、任务查询、取消和
视频下载路由。它还提供简单的同步 `/v1/chat/completions` 和 `/v1/completions` 适配器，
以文本形式返回视频 URL。

该实现只有一个 GPU 工作线程和一个容量为 32 的内存队列。任务串行执行。
重启后任务状态会丢失，但 MP4 和 JSON 文件仍留在磁盘上。服务没有清理保留输出的机制。

经检查，API 不验证授权标头。缺少 token 或 token 错误的请求仍能访问相同路由。
它也不提供 TLS、速率限制或用户隔离；因此必须在进程外实施访问控制。

硬编码了三种输出配置：

| 配置 | 帧数 | 标称时长 |
| --- | ---: | ---: |
| 640 x 384 | 124 | 5.17 s |
| 832 x 480 | 124 | 5.17 s |
| 640 x 384 | 243 | 10.13 s |

服务包含三个预编码提示词。尽管能力路由宣称支持任意文本提示词，镜像却缺少其自身提示词编码代码
所需的 Qwen3-VL-32B `processor`、`tokenizer` 和 `text_encoder` 目录，且已启用离线模式。
因此，任意提示词虽可作为任务被接受，却会在工作线程尝试加载缺失的条件编码器时失败。
只有随包提供的提示词嵌入得到可用性确认。

## 性能测量

所有测量任务均使用随包提供的 `example_2` 提示词、种子 42 和八次模型求值。
任务串行提交给已就绪的服务，因此报告的总耗时不包括排队等待。
首个 640 x 384 请求调用了 TorchInductor 编译工作线程。每种此前未使用过的形状的首个请求，
其第一次去噪步骤也较慢，因此下表将其与后续相同形状的运行分开列出。

| 配置 | 该形状的首个请求 | 后续相同形状的总耗时 |
| --- | ---: | --- |
| 640 x 384，124 帧 | 81.247 s | 76.973, 76.781, 76.942, 77.013, 76.942 s |
| 832 x 480，124 帧 | 125.651 s | 124.644, 124.761 s |
| 640 x 384，243 帧 | 152.424 s | 151.485, 151.521 s |

640 x 384 配置在首个请求后的五个样本，中位数为 76.942 秒，范围为 76.781 至 77.013 秒，
样本变异系数为 0.11%。形状编译后的两次重复测量，在 832 x 480 配置下平均为 124.703 秒，
在 243 帧配置下平均为 151.503 秒。这两组双样本的离散程度较低，但样本量不足以可靠刻画分布。

各配置汇总中，640 x 384 使用首个请求后的五个样本；另外两种配置使用全部三个任务，
所以其范围包含新形状的首个任务：

| 配置 | 实测输出时长 | 总耗时中位数（范围） | 去噪耗时中位数 | 解码/编码耗时中位数 | CUDA 峰值分配量中位数 | 总耗时/输出时长比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 640 x 384，124 帧 | 5.175 s | 76.942 s (76.781–77.013) | 65.425 s | 11.514 s | 60.813 GiB | 14.87 x |
| 832 x 480，124 帧 | 5.175 s | 124.761 s (124.644–125.651) | 102.611 s | 22.146 s | 61.056 GiB | 24.11 x |
| 640 x 384，243 帧 | 10.125 s | 151.521 s (151.485–152.424) | 128.444 s | 23.074 s | 61.138 GiB | 14.97 x |

`ffprobe` 确认每种配置都生成了 24 FPS 的 H.264 视频和 32 kHz 立体声 AAC 音频。
每种配置内的重复输出逐字节一致：

| 配置 | 文件大小 | SHA-256 |
| --- | ---: | --- |
| 640 x 384，124 帧 | 642,937 字节 | `7ac485b6a0918c7f89758506bf90a413bc9577340791a030e68bc8ec15843cd1` |
| 832 x 480，124 帧 | 1,123,394 字节 | `084b7f4405df7dac3b80e47a9580f0d4f5e73860d4d9a96d998bc942ec2df05d` |
| 640 x 384，243 帧 | 1,342,845 字节 | `2d6455a80fcba30f5b35da2a1d85077a660fc9f327d276a55799bff74b0672a0` |

一个为期 190 秒、采样间隔为一秒的 `nvidia-smi` 窗口，覆盖了一次 640 x 384 运行的剩余部分、
随后一次完整运行及其间的空闲时段。在 127 个 GPU 利用率非零的样本中，GPU 平均利用率为
97.57%，报告的 GPU 平均功率为 59.69 W。观察到的最高温度为 67 C；图形时钟查询值最高为
1,386 MHz。这是 GPU 功率，并非整板输入功率；遥测未提供风扇 RPM 或统一内存用量。
上表采用的是运行时自身测得的 CUDA 峰值分配量。

640 x 384、约五秒输出配置的耗时中位数，约为厂商产品页所列 38 秒的 2.03 倍；
该数据记录于 [Thor 概览](../../README.md#厂商公布的性能快照)。
832 x 480 配置的中位数约为其两分钟数据的 1.04 倍。本地服务提供的是 640 x 384、
10.125 秒输出配置，而非产品页所列的 15 秒配置，因此不比较两者耗时。
厂商使用的准确提示词、镜像构建版本、缓存状态、计时边界和输出验证方式仍未知；
这些比值是观察结果，并非受控回归测试结果。

## 测量现状与后续工作

对固定的随包提示词，目前已得到可重复的 640 x 384 稳态基线和三种配置的耗时矩阵。
这不能证明任意提示词的生成质量，也不能代表完整上游 H3 系统的性能。后续值得检查：

1. 在受控的服务重启后重复测试，以区分缓存恢复、模型启动、首个请求编译和特定形状编译的耗时。
2. 为另外两种配置各增加一次或多次形状编译后的重复测量，再判断其分布是否稳定。
3. 在记录 GPU 遥测的同时采集整板功率和风扇 RPM。
4. 修复自定义提示词条件编码器后，用有记录的提示词集合测试，再对质量下结论。
