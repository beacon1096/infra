# Renovate 与 Multica 合并门禁

## 目标

Renovate 发现依赖更新并创建拉取请求，但无权决定更新在运维上是否安全。主版本更新可能需要迁移、配置变更、分阶段发布说明，或 Renovate 无法推断的其他工作。

由人工或 Multica 代理审查拉取请求，并在必要时更新它。批准只对一个确切的头部提交有效；之后的任何提交都会使该决定失效，并重新启动审查。

## 流程模型

```text
Renovate PR 或更新后的头部提交
        │
        ▼
policy/merge-gate = pending
        │ 绑定 SHA 的审查任务
        ▼
Multica / 人工分析及必要修改
        │ 已签名的 approve / reject / human_required
        ▼
n8n 重新读取当前 Forgejo PR
        ├─ 不匹配/reject → policy/merge-gate = failure
        └─ approve        → policy/merge-gate = success
                                  │
                                  ▼
                         安排受保护的合并
                                  │ 必需的检查通过
                                  ▼
                            Forgejo 合并 PR
```

合并请求包含 `head_commit_id`。对于必需的检查、被否决的审查、冲突和过时分支，Forgejo 分支保护仍是最终的强制执行环节。

## 信任模型

| 主体 | 权限 |
| --- | --- |
| `renovate` | 创建和更新依赖 PR；不能合并到 `main` |
| Multica 代理 | 分析指定的一个 PR 修订版本并返回限定范围的决定；不获取 Forgejo PAT |
| 获授权的操作员 | 通过 Forgejo 审查批准他人创建的 PR，或使用绑定 SHA 的命令确认自己创建的 PR；初始允许名单为 `beacon1096` |
| `multica-gate` | 读取两个基础设施仓库并写入 `policy/merge-gate`；不能合并 |
| n8n | 验证审查能力凭证、写入策略结果并请求受保护的合并 |
| `multica-merger` | 只能通过其隔离的 n8n 凭据和 Forgejo 合并允许名单执行合并 |
| Forgejo | 强制执行受保护分支的要求，并拒绝过时或未经授权的合并 |
| GitOps、SOPS、集群和 n8n 管理员 | 已具有生产环境影响力、受信任的控制平面操作员 |

## 为什么执行器留在 n8n

n8n 已经负责创建获批的 `infra-private` 发布标签，因此本就是生产控制平面的一部分。若自定义合并服务仍由同一仓库、SOPS 接收者、Kubernetes 管理员和网络管理，就不会形成独立的安全边界。它会增加镜像、API、部署、升级路径和测试，却仍须信任同一批操作员。

只有当独立服务的密钥接收者、部署权限和管理员均与 n8n 分离时，它才值得引入。否则，专用的 n8n 工作流更精简，也更便于审计。

## 安全不变量

### 验证 Forgejo 事件的身份

公开的 Forgejo webhook 必须携带专用的授权值。未经认证的事件在更新事件状态、启动 Multica 任务、写入提交状态或生成通知之前，就会被 n8n 拒绝。这可防止调用方冒充 Renovate webhook 占用审查资源，或将门禁重置为 pending。

### 使用限定范围的审查能力凭证

n8n 签发短期有效的能力凭证，其中包含仓库、PR 编号、确切的头部 SHA、签发时间、到期时间和随机标识符。Multica 任务只收到该凭证，不会收到签名密钥。回调只能从经过验证的声明中确定作用范围；不能信任调用方提供的仓库和 SHA 字段。

该凭证最长有效 24 小时，且只能使用一次。验证签名和字段后，n8n 以原子操作将其随机 `jti` 插入以 `jti` 为主键的专用 PostgreSQL 表。`INSERT ... ON CONFLICT DO NOTHING` 只允许一次执行继续；并发或后续重放会在写入任何 Forgejo 状态或合并请求之前收到 HTTP 409。

回调客户端必须显式发送 `User-Agent: Multica-Review-Callback/1.0` 请求头。公开入口会以 Cloudflare 错误 1010 拒绝 Python `urllib` 默认用户代理等通用自动化客户端标识，请求因而无法到达 n8n。此请求头仅用于满足入口兼容性要求；授权仍取决于已签名、限定范围、一次性的能力凭证。

凭证使用采取失败即拒绝策略，并且发生在重新查询 PR 之前。如果后续 Forgejo 请求失败，同一凭证也不能重试；必须由新的 PR 事件签发新凭证。已使用的记录会保留至过期，并在七天宽限期后删除。重复使用不能授权其他 PR 或提交；重新查询 PR 和 `head_commit_id` 约束也会拒绝合并已关闭的 PR，或合并头部提交已变化的请求。

### 将判断与强制执行分离

Multica 评估运维风险并收集证据。回调有三种结果：

- `approve`：已审查的 SHA 包含必要的升级工作，并有充分的验证证据；
- `reject`：已知的不兼容问题或必要步骤尚未解决；
- `human_required`：决定需要结合环境、业务或人工判断，门禁保持 pending。

主版本变更不会被机械地拒绝，但涉及模式或数据迁移、存储格式、身份认证或授权、网络入口或路由、Talos、Kubernetes、Forgejo 等控制平面软件、破坏性操作，或证据不足时，默认结果为 `human_required`。绝不能仅为完成任务就把不确定性转为批准。

代理负责结合上下文作出判断；n8n 和 Forgejo 负责强制核验身份、仓库范围、当前 SHA、必需的检查、分支是否为最新以及合并权限等确定性事实。

审查代理被有意设计为不持有 Forgejo PAT。无法查询私有 PR、Multica 的 PR 关联表、Forgejo 提交状态或必需的检查，是预期的信任边界限制，并非针对变更本身的不确定性，单凭这一点也不构成 `human_required` 的理由。代理报告其能够取得的仓库和运行时证据；随后 n8n 使用隔离的凭据重新读取开放的 PR、确切的头部 SHA 和必需的检查。同样，缓存或工具不可用要与测试实际运行后失败分别报告。

### 将仓库内容视为不可信

PR 标题、描述、差异、发布说明和链接页面都可能包含试图操纵代理的指令。它们是证据，不是控制指令。只有审查操作手册定义代理的任务和回调协议。代理绝不会获得门禁或合并器的 Forgejo 凭据。

### 将批准和合并绑定到当前状态

在写入策略结果前，n8n 从固定的 Forgejo API 源地址获取 PR，并要求同时满足以下条件：

- 仓库是 `infrastructure/infra` 或 `infrastructure/infra-private`；
- PR 处于开放状态，目标分支为 `main`；
- 作者是 `renovate`；
- 当前头部提交等于已签名能力凭证中的 SHA。

只有获批结果才会安排合并。URL 根据经过验证的允许名单和整数形式的 PR 编号构造。请求将已审查的头部提交作为 `head_commit_id` 提交，且不强制合并。Forgejo 等待所有受保护分支要求得到满足，并拒绝头部提交已变化或过时的请求。

成功状态本身不会触发合并。只有在同一次 n8n 执行中验证已签名能力凭证、重新读取 PR，并使用 `multica-gate` 凭据写入门禁后，才会安排合并。因此，其他拥有仓库写入权限的主体即使发布另一个名为 `policy/merge-gate` 的状态，也无法仅凭此触发合并；若 n8n 的状态写入请求失败，执行会在使用合并器凭据之前停止。

### 隔离合并器凭据

`multica-merger` PAT 存放在 n8n 的加密凭据库中，只附加到固定的合并请求节点。不得将其作为 Pod 环境变量暴露、嵌入工作流 JSON、发送给 Multica，或交由 Renovate 复用。n8n 管理员仍是受信任主体；这种隔离可防止 webhook 数据和代理任务直接读取该凭据。

独立的 n8n 凭据 `Review Capability PostgreSQL` 在 Pod 初始化期间使用现有的 CNPG 应用 Secret 生成，并导入 n8n 的加密凭据库。其密码绝不嵌入工作流 JSON。工作流仅访问自身的 `multica_review_capability_consumptions` 表，并使用参数化查询。该凭据目前复用 n8n 应用数据库角色，因此相对于 n8n 管理员并不构成独立边界。待数据库管理与 n8n 控制平面分离时，可增设专用数据库角色。

## 失败时的行为

所有验证失败都按失败即拒绝处理：不安排合并。被否决或已过时的审查会写入或保留失败的门禁状态。Forgejo API 错误会向回调明确返回失败，并保留在 n8n 执行历史中。运维依赖故障使用 HTTP 424 和 JSON 错误正文：公开代理会把上游 5xx 正文替换为通用错误页面，而 424 能保留机器可读的结果，同时仍是非成功、失败即拒绝的结果。更新 PR 会产生新的 SHA 和新的 pending 门禁；对旧 SHA 的批准对其没有效力。

## Multica webhook Issue 去重

创建 Issue 的 autopilot 目前采用两项独立的重复检查：

1. webhook 入口使用从 `Idempotency-Key` 派生的投递标识，对重试去重；
2. 创建 Issue 时，若近期已有 autopilot、项目及规范化标题均相同的活跃 Issue，则抑制新建。

第二项检查可作为手动和定时运行的粗粒度安全保护，但不能用来识别 webhook 事件。本集成使用固定的通用 Issue 标题，因此多个不同的 Forgejo 拉取请求事件即使使用不同的幂等键，也可能生成同一个标题。标题检查随后只创建第一个 Issue，却错误地将其余运行标记为 `skipped`，原因是 `recent duplicate autopilot issue`。

下游补丁 [`multica-webhook-issue-dedup.patch`](../../../ci-cd/patches/multica-webhook-issue-dedup.patch) 以持久化的 webhook 投递记录作为权威的去重边界：

- 使用相同投递标识重试时，仍复用已有运行；
- 不同投递即使标题相同，也会创建不同的 Issue；
- 重放仍视为新投递，因此会执行所请求的工作；
- 手动、定时以及旧式非持久化运行仍保留基于近期标题的安全保护。

实现检查的是 `run.WebhookDeliveryID.Valid`，而非文本形式的 `source` 字段。这样例外只适用于受数据库唯一性约束保护的持久化投递，避免错误标记的内部调用绕过去重。无需迁移数据库模式，也无需更改 n8n 工作流。

补丁包含使用 PostgreSQL 的回归测试：通过同一个创建 Issue 的 autopilot 发送两个 `Idempotency-Key` 值不同的 webhook 请求，并验证各自的运行引用不同的 Issue。还用现有测试核验了普通分派仍会抑制近期同标题的 Issue。在一次性 PostgreSQL 实例中应用全部上游数据库迁移后，两项测试均通过。

该修复还于 2026-09-16 在生产数据库上完成冒烟测试。两次投递生成相同的 Issue 标题，但使用不同的幂等键，最终创建了各自独立的运行和 Issue；使用第一个键重试返回 `duplicate`，并复用其投递记录。测试后立即恢复了官方 `v0.4.24` 镜像。

不同的拉取请求修订版本有意保留各自独立的运行和限定范围的能力凭证：针对一个头部 SHA 的决定绝不能授权另一个 SHA。为了在保持这一安全属性的同时避免同一个 PR 留下多个可处理的 Issue，n8n 在接受新分派后会协调 Issue 状态。它查询相同仓库和 PR 编号的先前分派记录，并通过 Multica 验证每条记录中保存的
autopilot 与运行的绑定关系、取消所有仍在排队或执行中的先前运行、读取绑定的 Issue，并仅将尚未进入终态的先前 Issue 改为 `cancelled`。状态为 `done` 或已是 `cancelled` 的 Issue 绝不会被降级。新 SHA 对应的 Issue 是唯一保持活跃的 Issue；取消不会沿用旧的结论，旧代理也无法在审查过时后继续写入。

这一协调过程刻意设计为幂等。并发投递可能读取同一个先前 Issue，但重复设置 `cancelled` 的最终状态相同。所有 Issue 标识符均来自保存的运行绑定关系，而非代理提供的 URL 或标题。如果无法读取或验证 Multica，就停止该协调分支，而不会猜测 Issue 的身份。

临时下游镜像由 `multica-backend-oci` flake 输出以可复现方式构建。它获取固定版本的上游 `v0.4.24` 源码，应用上述补丁，构建静态 Go 二进制文件，并生成标记为 `0.4.24-beacon.1` 的 OCI 归档。Forgejo 构建工作流将这个不可变的版本标签发布到 `forgejo.beaco.works/infrastructure/nix-fleet/multica-backend`。部署则通过另一项 Multica HelmRelease 变更完成，且只有在注册表标签可匿名访问后才进行。这样的顺序可防止 Flux 协调镜像尚未发布的清单。

发布任务通过从标准输入填充的临时 `skopeo` 认证文件登录。不得通过 `--dest-creds` 传递注册表凭据：命令参数会显示在运行器的进程表中。退出陷阱会删除认证文件；若发现凭据曾暴露在进程表中，则轮换注册表 PAT。

## 拉取请求验证

不使用凭据的 Forgejo 工作流 `Nix Validation` 会对每个拉取请求求值所有 flake 输出，并运行 n8n 策略回归测试。它不会获得 Attic、注册表、SOPS、门禁或合并器凭据。全套机器配置构建仍在合并后和发布工作流中进行；如果依赖更新影响特定主机或部署产物，Multica 可以要求额外进行针对性构建以提供证据。

## 非 Renovate 拉取请求

受保护的 `policy/merge-gate` 状态上下文适用于每个拉取请求。普通 PR 在创建、重新打开或更新时，当前 SHA 的门禁会设为 pending。如果操作员不是 PR 作者，则通过 Forgejo 的常规审查界面批准。Forgejo 有意禁止作者批准自己的 PR，因此允许名单中的作者改为在 PR 上发布内容严格为 `/approve <full-40-character-head-SHA>` 的评论。

审查或评论 webhook 仅用于唤醒流程。n8n 不信任其中声称的审查人、命令或结论。它通过固定的 Forgejo API 源地址重新读取开放的 PR，以及该 PR 的审查记录或指定评论，然后要求同时满足以下条件：

- 仓库是两个基础设施仓库之一，目标分支为 `main`；
- PR 作者不是 `renovate`；
- webhook 中的 PR 头部提交与当前 PR 头部提交相同；
- 对于审查记录，其 `commit_id` 是当前头部提交，且既未过时，也未被撤销；
- 对于作者确认，重新读取的评论 ID 与 webhook 中的 ID 相同，正文仅包含 `/approve` 加上当前头部提交的完整 SHA，不接受缩写 SHA；
- 审查人或确认操作的作者位于明确的操作员允许名单中，初始名单为 `beacon1096`。

只有满足这些条件，`multica-gate` 才会将该 SHA 标记为成功，隔离的 `multica-merger` 凭据才会使用相同的 `head_commit_id` 请求受保护的合并。重放旧审查记录无法批准已变化的头部提交。Multica 的决定继续使用独立的已签名能力凭证路径；代理无法从 PR 可控内容伪造这两类事件中的任何一种。

作者确认是绑定验证后修订版本的第二次操作，而不是独立的双人复核。这是明确的单操作员例外：目前获授权以 `beacon1096` 身份操作的代理，与该 Forgejo 用户属于同一主体，门禁无法区分代理和人工操作员。长期而言，应使用代理专属的 Forgejo 身份恢复这种区分；在此之前，审计记录只能证明共享主体确认了哪个确切修订版本，无法证明点击者是人工还是受委托的代理。

## Renovate 合并队列

获批的 Renovate PR 会进入由 PostgreSQL 支持的先进先出队列，而不是在回调执行中直接合并。这样，每次合并到 `main` 都不会迫使其他所有已获批的依赖 PR 再次接受代理审查。

批准时，n8n 读取 PR 的合并基点与已审查头部提交各自的递归 Git 树。它计算按路径排序的规范化差异，记录每个变更叶节点的路径、类型、模式、基点 blob ID 和头部 blob ID，并将该差异的 SHA-256 摘要连同仓库、PR、确切的已批准头部提交、Multica 能力凭证 JTI 及 24 小时有效期一并保存。树若被截断、不可读取或过大，就按失败即拒绝处理。刻意不使用 `git patch-id`，因为它对空白字符的规范化弱于所需的字节级树身份校验。

n8n 工作流 `Renovate Merge Queue` 每次只租用一个活跃队列项。它重新读取 PR，要求 PR 仍处于开放状态、作者为 `renovate`、目标分支为 `main`。如果 PR 的合并基点落后于当前目标分支的头部提交，隔离的合并器凭据就请求 Forgejo 更新 PR 分支，然后释放租约。由此产生的 synchronize webhook 会让 `policy/merge-gate` 保持 pending；只要该队列记录仍活跃，就会抑制重复的 Multica 分派。

PR 包含当前目标分支内容后，工作进程重新计算树差异。只有摘要和变更路径数均完全匹配，批准才会延续到新的头部提交。因此，`main` 上其他位置的变更不需要再次审查，但已批准的路径/blob/模式/类型集合只要有任何变化，就会阻塞该队列项。被阻塞的队列项通过已认证的 infra-ci webhook 作为新的 `synchronize` 事件送回。该事件仅用于唤醒流程：infra-ci 为更新后的头部提交创建新能力凭证，回调在接受决定前仍会重新读取 Forgejo。绝不根据旧提交状态推断批准。专用的事件变体可防止先前 Forgejo 的 `synchronize` 投递经事件去重抑制再次审查。新审查请求被接受后，工作进程通过保存的能力凭证 JTI 找到旧 Issue，并将这个严格绑定的 Issue 标为 `cancelled`；新头部提交保留自己的 Issue 和能力凭证。

字节级规则有意将对同一文件的无关编辑也视为差异发生变化。因此 Renovate 将所有 `mise` 管理器更新归入一个 PR，以减少 `wanxiang/.mise.toml` 中的冲突，同时不削弱门禁。

### 同一文件的变基事件与决定

PR #33（`go-task`）和 #39（`pipx`）创建于 `mise` 分组规则生效之前。两者分别修改 `wanxiang/.mise.toml` 中不同的赋值。一个 PR 合并后，对另一个 PR 变基会改变该文件的基点和头部 blob ID，即使它自身的版本赋值并未变化。合并队列正确地判定确切树差异检查失败，并请求再次进行 Multica 审查。串行合并这两个旧 PR 时，这种情况又发生了一次。过程是安全的，但增加了本可避免的审查。

曾测试 Forgejo 已认证的 `pulls/{number}.diff` 端点，评估它能否替代现有不变量。规范化摘要可以忽略差异块行号，从而在同一文件发生无关编辑时保持不变。`pulls/{number}/files` 端点不包含补丁内容，因此必须从原始 diff 端点获取数据。最终没有采用这一做法：忽略位置或上下文，可能把在不同语义位置应用的相同增删行误认为已批准的变更；保留足以防止此问题的上下文，又会重新引入邻近依赖编辑之间的冲突。其运维收益有限，却会削弱当前字节级的批准绑定。

最终决定保留失败即拒绝的树摘要校验，从源头解决冲突。Renovate 将 `mise` 管理器更新归入一个 PR，使 `.mise.toml` 的新更新共享同一份已审查差异。已开放的旧 PR 在处理完之前可能仍需重复审查。未来若要放宽规则，必须建立理解管理器语义的模型，并加入明确的歧义测试；通用的仅按行计算的补丁摘要不足以保证安全。

证明等价后，`multica-gate` 只将当前头部提交标记为成功。工作进程重新读取聚合后的提交状态，只有所有必需的检查均报告成功，才会使用 `multica-merger`。合并请求包含当前的 `head_commit_id`、禁用延迟合并、不使用强制合并，并仍受 Forgejo 分支保护约束。若并发合并使队列项过时，它会返回队列，进入下一轮确定性的更新流程。

成功合并后，关闭 Issue 的操作绑定到保存的确切 Multica 运行、autopilot 和 Issue 标识符。autopilot 运行本身不作为完成信号：由 webhook 触发的运行在回调获批后仍可能处于 `issue_created`。Forgejo 确认合并后，队列改为查询绑定 Issue 的活跃任务运行，等到没有活跃任务时才将 Issue 标为 `done`。这避免关闭器与审查代理最后一次写入 `in_review` 发生竞争。已合并但尚未记录 Issue 已关闭的行，在后续队列运行中仍可参与幂等协调。工作流在本地筛选活跃状态，因为较早部署的 Multica 版本会忽略 API 的 `active=true` 查询参数，并返回完整的任务历史。

队列状态为 `queued`、`updating`、`waiting_ci`、`merging`、`merged`、`blocked` 和 `expired`。领取队列项使用短期数据库租约和 `FOR UPDATE SKIP LOCKED`；批准在原始能力凭证的 24 小时有效期结束时过期。

## 合并就绪状态与可观测性

人工批准的 PR 继续走即时合并路径。使用合并器凭据之前，n8n 会重新读取确切获批 SHA 在 Forgejo 中的聚合提交状态。状态失败、缺失或无法读取时，流程都不会到达合并器节点。合并仍绑定 `head_commit_id`、不使用强制合并，并受分支保护约束。

策略结果以纯文本通知发送到 Forgejo CI Matrix 房间。通知涵盖无效回调、能力凭证重放、过时的 SHA、`reject`、`human_required`、被阻塞或失败的合并、排队中的合并及已完成的合并。通知包含仓库、PR、确切的 SHA、可用时的证据 URL 和 n8n 执行 URL，但绝不包含能力凭证或其他凭据。回调响应与通知投递并行进行，因此 Matrix 故障不会使已接受的决定变成一次与凭证单次使用限制冲突的重试。

Renovate 合并完成后，n8n 通过绑定已签名能力凭证 JTI、仓库、PR 编号和头部 SHA 的分派记录，定位最初的 Multica autopilot 运行。待其活跃代理任务退出后，n8n 使用专用成员身份 `multica-closer.no-reply@beacoworks.xyz` 将该运行的 Issue 标记为 `done`。此查找不信任代理提供的 Issue URL。排队中的合并在 Forgejo 确认合并且审查运行空闲之前，始终保持 `in_review`。

Multica 目前不支持为个人访问令牌设置权限范围。因此，关闭器具有普通工作区成员权限；n8n 将其令牌隔离在仅附加到固定的运行读取节点和 Issue 状态节点的凭据中。不得向代理、回调负载或工作流 JSON 暴露该凭据。

## 延后实施：由 webhook 触发 Renovate 运行

当前 Renovate OSS 进程是由定时器调度的一次性 systemd 服务。因此，Dependency Dashboard 复选框的变更会在下次定时运行时处理，而非立即处理。应保留定时器作为可靠的后备机制。

如果今后需要缩短延迟，Forgejo 可向 n8n 发送相关的 Issue webhook，由 n8n 通过专用且受限的 SSH 身份在 Renovate 所在主机上启动 `renovate.service`。这条路径不得向 n8n 提供通用 shell。拟采用的身份应受 OpenSSH 强制命令和 `restrict` 限制，仅被授权执行 `systemctl start renovate.service`。此外，n8n 只能接受符合预期的仓库、Dependency Dashboard Issue、事件动作及操作者。systemd 仍负责抑制并发重复运行，现有定时器仍保持启用，以应对 webhook 遗漏。

不要为此便捷触发方式暴露通用的 systemd HTTP 端点，也不要复用管理员 SSH 凭据。该集成目前有意保持未启用状态。
