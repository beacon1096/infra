# Agent Nix 构建的信任边界

Coder 编码代理工作区使用精简的单用户 Nix 安装。镜像有意设置 `sandbox = false`，并将 `build-users-group` 留空，因为普通 Kubernetes Pod 不具备 Nix Linux 沙箱所需的挂载和用户命名空间权限。这足以支持 Home Manager 激活、求值以及可信的交互式工作，但不能为拉取请求提供的派生项建立安全边界。

没有 Nix 沙箱时，构建进程可以看到工作区文件系统的更多内容、使用 Pod 的网络，并影响可写的运行时状态。工作区目前在容器内以 root 身份运行，因此剩余的边界是容器隔离，而非 Nix。必须确保 `/homeless-shelter` 不存在：Nix 将它用作刻意设置的无效构建 HOME；如果该路径存在，Nix 会拒绝无沙箱构建，因为这会让构建进程看到主机状态。

## 短期策略

编码代理可以运行：

- `nix flake show`、`nix eval`、解析以及其他仅执行求值的检查；
- 不会实际构建由 PR 控制的 Nix 派生项的针对性测试；
- 常规的语言、模式、格式和 Shell 验证。

代理不得在本地实际构建来自 PR 的完整 NixOS 或 nix-darwin 闭包。Forgejo 对准确的头部提交 SHA 所要求的状态提供完整构建证据。如果必需的 CI 状态缺失或无法得出结论，代理应返回 `human_required`，而不是以本地无沙箱构建替代。

镜像只信任无需工作区密钥即可使用的缓存。它包含官方 `cache.nixos.org` 签名密钥，并从 substituter 列表中移除私有 Attic 缓存。在能够注入限定范围的只读凭据，且不会向 PR 控制的代码暴露更广泛的基础设施权限之前，不得公布私有缓存。

Coder 模板按摘要固定编码代理镜像。更改此配置后，等待 `build-and-push-coding-agent-oci` 发布镜像，解析新的镜像仓库摘要，更新模板中的固定摘要，并重新创建或重启受影响的工作区。仅发布 `latest` 不会改变现有工作区或其模板中固定的版本。

## 中期方案

### 继续使用 Forgejo CI

这是默认且成本最低的方案。现有受保护状态已经绑定到准确的提交；CI 仍在等待或失败时，合并关卡会保持关闭。无需新增凭据或调度器。代价是代理无法请求工作流矩阵之外的探索性构建。

预计实施成本：仅需修改配置和操作手册，无需新增服务。如果代理以后需要在受限范围内选择额外的构建目标，可以添加 workflow-dispatch 输入。

### 通过 n8n MCP 暴露受限验证能力

n8n MCP 可以将经过审查的验证工作流转化为供 Multica 代理调用的具名工具。这使编排逻辑不再依赖模型提示词：较小的模型可以请求 `validate_nix_pr`、`render_helm_release` 或其他范围明确的操作，而无需构造 Shell 命令、选择构建机或解释原始调度器状态。工作流返回结构化结果和证据 URL，供审查决策使用。

不要通过 MCP 暴露通用工作流执行、任意命令、仓库 URL、flake 属性或 Kubernetes 对象。每个工具都必须接受范围较小且经过验证的 schema，对仓库和目标使用允许列表，以独立凭据重新读取 PR 和准确的头部提交 SHA，并在有沙箱的 CI 或专用构建机路径上执行。凭据保留在 n8n 和运行器中；MCP 参数和结果均不得包含凭据。长时间运行的调用需要执行 ID、受限日志、取消和超时机制，以及绑定到所请求 SHA 的不可变结果。

调用 MCP 不等于批准。现有合并关卡仍需验证已签名的审查权限、当前 PR 身份、必需检查和分支是否为最新。工作流结果应区分测试失败与容量、缓存或工具不可用，避免代理将基础设施故障误判为兼容性问题。

先使用 Forgejo 工作流中已有的验证命令，而不要另建一套测试实现。首个原型应涵盖一次 Nix 求值和一次 Helm 渲染；完成 schema、授权、重放、超时、取消、恶意输入及结果绑定测试后，再开放更多工具。

### 将 Forgejo 构建机复用为 Nix 远程构建机

三台 Forgejo 构建机可提供构建容量，因为维护会轮换进行，且多数机器保持在线。Nix 本身会依据平台、必需特性、`maxJobs`、`speedFactor` 和负载，在多个远程构建机之间调度派生项。因此，Multica 工作区可以使用本地 Nix 守护进程作为分发器，并设置本地 `max-jobs = 0`，防止构建回退到无沙箱的工作区。

同样的职责划分也适用于 Forgejo 任务。运行器仍是 CI 控制会话：检出准确的提交、启动 `nix build`、流式传输日志、传递取消请求并报告受保护状态。它无需自行选择或执行派生项。运行器的 Nix 客户端可以在禁用本地构建的情况下，将派生项提交到同一个远程构建机池，由 Nix 决定放置位置并执行。目前的构建机则设置了 `distributedBuilds = false`，在 Forgejo 选中的节点上本地构建。因此，这是明确的未来架构变更，并非当前行为的描述。

两种 Nix 布局存在实质区别：

- 使用普通分布式构建机时，运行器或工作区守护进程仍是主存储和调度器。它将派生项发送到远端，但把输出接收到自身存储。因此，每个客户端仍需处理本地存储增长、垃圾回收及部分 substituter 配置。
- 使用专用远程存储及分发器时，CI 和代理在整个操作过程中都访问该存储，其守护进程可以将构建分发给工作节点池。这样便可集中管理存储保留、垃圾回收、优化、读取侧二进制缓存配置以及构建准入。如果目标是轻量 Forgejo 运行器，这就是预期的最终形态。

远程存储布局需要针对日志获取、取消、结果路径处理、失败构建诊断和 OCI 输出进行明确测试。需要在本地使用结果的工作流，可能仍需显式复制结果或增加远程执行步骤。

不要仅为了省去工作流步骤，就给共享分发器配置默认可用的 Attic 写入凭据。Multica 代理可以向同一服务提交构建，因此自动上传会让代理请求的输出进入可信缓存。构建机配置应保留 Attic 读取能力和公开的验证密钥，但缓存发布仍须是经 Forgejo 授权、使用限定范围写入凭据的操作。重复的登录、路径验证和推送逻辑可以移入经过审查的辅助程序，但不能将这项信任决策移入构建机。

这确实涉及调度，但不存在一个全局队列。每个工作区都有独立的 Nix 守护进程，这些守护进程不了解 Forgejo Actions 队列或其运行器的排空状态。如果两个系统共用机器，构建机侧的准入控制必须成为共同边界：进入维护状态时，排空 Forgejo 运行器并拒绝新的 Nix SSH 会话，等待 Actions 任务和持有租约的 Nix 会话全部结束，然后才修改主机。其余机器继续对两套调度系统提供服务。

依赖此行为之前，需要测试某个端点被排空或无法访问时，新构建是否会分配到其他端点；还要分别测试构建开始前和构建期间连接中断的情形。不要假定所有传输故障都具有相同的重试行为。应在构建机侧施加并发和资源限制，防止独立的 Nix 客户端挤占 Forgejo 任务的资源。

预计实施成本为中等：受限身份和客户端配置约需一至两个工程日；共享准入、排空集成、资源限制及故障转移测试还需两至三个工程日。无需定制调度服务。

### 增加专用远程构建机

独立的 NixOS 虚拟机是更清晰的交互式构建设计。它应启用 Nix 沙箱，仅开放受限的 Nix SSH 协议，不持有 Forgejo、Multica、部署、SOPS 或 Attic 写入凭据，并且只接受来自编码代理命名空间或身份的流量。设置客户端 `max-jobs = 0`，以防 PR 派生项回退到无沙箱的本地存储。在允许代理访问前，先设置并发、磁盘、构建时长和垃圾回收限制。

清理必须与构建会话协调，不能安排在固定的维护时间窗口：

1. 强制命令 SSH 包装程序在整个 Nix 协议会话期间持有共享租约，并记录最后一个会话结束的时间。
2. 清理控制器评估空闲宽限期、两次清理之间的最短间隔以及磁盘高水位和临界水位。systemd 定时器可以评估这些条件，但不能仅凭实际时间流逝就启动清理。
3. 清理前进入排空模式，拒绝或排队等待新会话，等待所有共享租约结束，再获取独占维护租约。获取独占租约可消除空闲检查与新连接之间的竞态。
4. 执行有界的垃圾回收和存储优化，记录结果及回收的空间，即使失败也要退出排空模式。待执行的非紧急清理可以让位于新到达的代理请求。

Nix 临时根可防止正在进行的实际构建所需内容被垃圾回收，但无法解决准入竞态、磁盘及 I/O 资源争用或服务可用性问题。因此，仍须使用外部租约和排空协议。达到临界水位时的紧急清理应停止接收新任务，但除非另行记录的资源限制或执行超时已经触发，否则不得终止正在进行的构建。

现有 Harvester 虚拟机和 NixOS 模块模式可以复用，但这仍会增加一个机器生命周期和容量池。预计实施成本为中等：受限构建机约需一至两个工程日；准入、租约、清理、可观测性和故障测试还需两至三个工程日。如果要求主机维护期间严格保持可用性，则至少需要两台构建机，并实现经过测试的相同排空和准入行为。专用构建机池避免了与 Actions 争用资源，但仍可使用 Nix 的派生项调度能力。

## 决策

目前以 Forgejo CI 作为完整构建的权威环境。在共享准入和故障转移经过测试后，Nix 远程构建机路径可以复用多数机器保持在线的运行器池，供代理进行探索性构建；其结果不能替代绑定准确提交的受保护 CI 状态。仅当与 Actions 的资源争用或更高的可用性要求足以证明额外容量有必要时，才迁移到专用构建机池。不能因为无法在 Coder 本地实际构建，就放宽合并关卡。
