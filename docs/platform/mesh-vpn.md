# MeshVPN 中间层与迁移路线 [WIP]

目标不是把 Tailscale 配置项改名，而是让站点服务访问、跨站路由和上层应用不直接依赖某一个 MeshVPN。长期方向是自建 NetBird；过渡期 Tailscale 与 NetBird 并存、灰度验证，再按前缀迁移。这里记录设计和已有实验，不表示 NetBird 已成为生产路由。

## 分层与边界

每个站点由该站点主网络命名空间中的 sing-box 作为唯一 TUN 与出站决策点；不是全网共用一台 sing-box。Tailscale、NetBird 作为可并行运行的用户态网络提供者，各自暴露不同的 SOCKS 端口。站点的 sing-box 根据目的前缀选择提供者；上层服务尽量只关心稳定的站点网段或服务名，不直接选择某个 VPN 客户端。提供者自身进程必须绕过 sing-box 拦截，否则其控制面或连接探测会递归进入自身隧道。

这一形态适合先处理 TCP/UDP 服务流量，但用户态 SOCKS 并非完整的三层站点互联：源地址保留、任意 IP 协议和服务端主动 UDP 需要单独验证，不能从普通 TCP 连通性推断。是否把提供者放进容器、虚拟机或独立网络命名空间，是为解决隔离问题时的升级选项，不是第一版必需条件。

Mesh 中间层至少要区分：

- **传输层**：提供者的 SOCKS 地址、端口、进程绕行、可接管前缀和状态。
- **路由归属**：同一个目的前缀在本地 sing-box 与对外 OSPF 中只有一个活动提供者；备用提供者可以运行，但不能同时宣告同等优先级的路由。
- **名称解析**：域名到地址的服务发现独立于传输层。MagicDNS 是 Tailscale 专属行为，不应成为公共 MeshVPN 接口的一部分；Caddy、hosts、未来 SSH CA 等也属于更上层。

站点前缀与提供者选择可以在私有仓配置，公共模块只提供可复用的表达和路由生成。身份凭据仍由 sops 管理，不应进入公开设计文档或 Nix store。

## 已有实现与现场试验

2026-09-19 的 Codex 会话记录：私有仓 `main` 已有第一步 `beacoworks.mesh.socksProviders.<name>`，包含 `enable`、SOCKS 地址/端口、`routeCidrs`、`processNames`。启用的提供者会生成 sing-box SOCKS 出站、目的前缀路由和进程绕行；光谷配置启用 Tailscale、预留未启用的 NetBird。该仓库的当前文档工作分支仍可能基于旧版私有模块，查配置时应以目标分支和实际部署的系统版本为准。

这还不是完整迁移控制面：没有完整的站点归属模型、根据健康状态切换活动提供者的机制，也没有相应的 OSPF 发布与故障撤销。`routeCidrs` 能描述本地 sing-box 的选择，不等于整个站点已经通过 OSPF 使用新提供者。

Gen10 Plus 的用户态 Tailscale 现场试验验证了部分 Tailnet 对端及 `172.16.80/100/101` 流量，但 `172.16.10.1` 失败；当时存在 `.10/23` 与 `.10/24` 重叠宣告，尚未证实唯一根因。另一次公网失败来自误解 sing-box `route_address`：非空列表会替代默认接管范围，不是追加。分支随后修正了这一点并构建通过，但没有进行第三轮现场切换；主机已回滚为原内核 Tailscale、第 52 号路由表和 BIRD 路径。**构建成功或分支合入不等于现场已迁移。**

原内核模式 Tailscale 还出现过“经其他子网路由器可达的私网端点被选为直连”的隧道套隧道问题。短期防递归方案依赖内核模式的 `fwmark`/`ip rule`；切到用户态后它不再适用，须改由提供者进程绕行与明确的出站路径避免递归。不要把所有非直连 RFC1918 地址一律拦掉：拓扑中也存在合法的、经路由可达的底层网络。

## 灰度顺序

1. **保持行为的抽象**：先用公共 MeshVPN 表达生成既有 Tailscale 路由，核对 sing-box JSON、默认 TUN 接管范围、DNS 与其他出口规则，暂不引入自动故障切换。
2. **并行旁路验证**：自建 NetBird 控制面，在少数测试主机上以不同 SOCKS 端口与 Tailscale 并行；先不接管整站前缀，也不向 OSPF 发布其路由。验证目标版本的用户态网络栈与 SOCKS 能力，以及凭据隔离。
3. **小范围试点**：选择单机或极小前缀，明确唯一活动提供者；分别测 TCP、普通 UDP、服务端主动 UDP、DNS、故障恢复及递归连接端点，并保留立即切回 Tailscale 的路径。先解决 `.10` 重叠前缀，再测试跨站路由。
4. **按前缀迁移**：逐组把 `172.16.x.x` 前缀从 Tailscale 切给 NetBird。只有提供者健康和站点路由都通过验证，才允许 OSPF 宣告；失败时先撤销路由避免黑洞，再恢复 Tailscale 作为活动提供者。ZeroTier 可保留为人工应急路径，不参与同优先级自动竞争。

目前缺失的关键组件是前缀归属校验、唯一活动提供者、提供者健康检查及 OSPF 路由撤销。它们完成之前，MeshVPN 中间层只能作为本机流量选择与实验入口，不能宣称完成站点灰度。

## DNS 是独立工作项

当前 `msi-claw` 等工作站由 sing-box 独占 TUN，系统 `tailscaled` 提供本地用户态 SOCKS，并不接管宿主 DNS。早期方案把 MagicDNS 写成 `100.100.100.100` 经 SOCKS 应答；当前私有模块改用假 IP（`fake-IP`），让保留域名的连接走 Tailscale SOCKS 并在代理侧解析。此前 `getent hosts` 失败的观察属于带日期的历史问题，是否仍存在须重新实测。

NetBird 的用户态网络栈/SOCKS 与 Tailscale 的 MagicDNS 不能默认视为对等；未来可用独立的中央解析器或只按 IP 访问，不应以 DNS 差异阻塞传输层的第一步抽象。旧的 `k8sTransparentProxy` / `k8s-sing-box-image` 来自已放弃的 Talos/Cilium 出口方案，清理与当前 MeshVPN 灰度是不同工作项；镜像现状见 [NixOS 容器镜像](container-images.md)。
