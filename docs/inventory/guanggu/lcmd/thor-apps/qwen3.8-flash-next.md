## Lazycat 管理应用

已安装的软件包为 `cloud.lazycat.aipod.qwen38-flash-next`，显示名称为
“Qwen 3.8 Flash Next 未审查版”。软件包说明宣称默认调度八个请求、上下文长度为 265K，
支持 128K 至 320K 上下文。检查到的持久化部署配置如下：

- 模型 ID 为 `qwen-3.8-flash-next-uncensored`，模型版本为 `0.1.40`；
- 模式为 `multi-concurrency`，请求并发数为 8，`maxNumSeqs` 为 8；
- 上下文长度为 265,000；
- 预估设备内存为 112 GiB；
- 运行时镜像为
  `registry.lazycat.cloud/catdogai/qwen38-flash-next:runtime-134-0.1.6`.

原始 LPK 的 SHA-256 为
`7b273c0dddbbec9630caee5172ee97ea61746f474d0f2d6203bbd9de002f23cf`.
其内嵌管理镜像通过以下摘要固定版本：
`sha256:b4e7182dca6a9da68d842217cb3bc18c91a940f52c872c79fa7b26d28f9c2894`.

当前重启记录显示，从服务启动到就绪耗时 367.66 秒。首次安装还需要传输并导入
142.75 GB 的运行时归档；这一次性传输不计入重启耗时。

## 算力运行时

ARM64 运行时镜像的摘要为
`sha256:f028c1b7ce2c6951c17d38fd2a20b4031971b5cea8ff3b31b99d41690325ce87`,
创建日期为 2026-09-06，本地镜像大小为 142.75 GB。其标签标明 vLLM 版本
`18f658bb3185779ee58999a328246d09886d568b`，以及检查点
`gorbatjovy/qwen3.8-flash-next-abliterated-NVFP4-plefp8` 的版本
`2065365912e46b205c64a70ac5b85b4869674d31`.

观察到的软件版本：

| 组件 | 版本 |
| --- | --- |
| Python | 3.12.13 |
| Torch | 2.11.0 |
| vLLM | `0.0.0+18f658bb3185` |
| FlashInfer | 0.6.18 |
| Triton | 3.6.0 |
| Transformers | 5.12.1 |
| Humming 原生内核 | 0.1.13 |

镜像包含 17 个带索引的权重文件，合计 125.90 GiB。PLE 表在磁盘上占 47.7 GiB，
使用 32 个 CPU 工作线程、固定内存暂存缓冲区且不做完整预热，以 128 个 FP8 分片进行内存映射。
vLLM 报告加载的目标模型和草稿模型共占 78.67 GiB。观察到的重启中，完整模型加载阶段耗时
233.94 秒；随后图和引擎初始化耗时 22.80 秒，再进行多模态和请求形状预热。

原始检查点的原生上下文长度为 262,144 token。运行时以系数 1.220703125 构建
320,000 token 的 YaRN 视图，但此部署对输入与输出 token 总数设置了 265,000 的硬上限。

主要服务配置：

| 设置 | 观察值 |
| --- | --- |
| 调度器 | 8 个序列，批处理 8,704 个 token |
| KV 缓存 | 12.8 GiB，可容纳 351,829 个 token |
| 前缀缓存 | 禁用 |
| 推测解码 | 一层 MTP，K16 |
| CUDA 图 | 仅完整解码，捕获大小为 1 和 17 |
| Mamba 状态 | BF16 |
| GDN MTP 解码 | 回退至 Triton |
| PLE | FP8 内存映射、固定内存暂存区、每块 2,048 行 |
| 网络 / IPC | 主机网络模式 / 主机 IPC |
| 容器权限 | NVIDIA 运行时、`IPC_LOCK`、非特权 root |

报告的 KV 容量仅相当于同时处理 1.33 个完整的 265,000 token 请求。
因此，“八路并发”是较短请求的调度器上限，不代表可同时容纳八个最大上下文请求。

目标检查点使用 ModelOpt W4A16 NVFP4。运行时在 SM110 上为 NVFP4 MoE 路径选择了 Marlin，
并安装了自定义 NVFP4 CUTLASS 全词表输出头。FP8 和 FP4 输出头开关均已设置，
但补丁的转换与分发代码优先选择 FP4；启动日志确认了 NVFP4 候选项。
由于缺少原生多 token GDN 算子，运行时还使用 Triton GDN 回退路径。

配置和环境通过 `VLLM_QWEN4_DISABLE_COOP_TOPK=1` 请求禁用 cooperative-top-k。
然而，此 vLLM 构建版本将该变量报告为未知，已安装的稀疏索引器源码也不读取该变量，
其 SM110 选择器条件仍然存在。因此，没有执行追踪就不能认为预期的禁用已生效。
这与[先前本地实验](../../../../inference/thor/model/qwen3.8-flash-next/original.md#确定性-qsa-选择正确性回归)中
验证过的确定性选择器补丁不同。

## API 与功能观察

服务提供标准 vLLM OpenAI 兼容的聊天、补全、响应、分词和指标路由。启动时未传入 API key 参数：
无授权、使用错误 bearer token 和使用已配置 token 的模型列表请求均返回 HTTP 200。
模型进程也没有 TLS。因此必须在外部提供网络访问控制。

Lazycat 客户端配置宣称支持文本和图像输入、推理及 16,384 个输出 token，默认采样参数为
temperature 0.3、top-p 0.95 和 top-k 20。运行时启用了 Qwen3 工具调用和推理解析器。
此次未评估工具调用及推理质量。

一次多模态冒烟请求使用内存中的 32 x 32 纯红色 PNG，要求输出一个小写颜色词。
模型在 9.205 秒内返回 `red`。该请求使用 95 个提示 token 和两个补全 token。
这确认目标模型的视觉路径可用，并不能代表整体视觉质量。首个真实图像请求触发了两次额外的
Triton JIT 编译，说明启动预热未覆盖这一实际图像形状。MTP 日志还指出，外部多模态嵌入
不会传给草稿模型；多模态请求的草稿输入仅包含文本。

## 单路流式测量

三个工作负载和计时定义与先前本地实验相同。每个工作负载先进行一次不计入报告的预热，
然后顺序执行三次测量请求。temperature 为零，关闭思考模式，并提供固定种子。
中文和代码使用固定输出长度；JSON 使用常规停止处理。解码速率按
`(completion tokens - 1) / (stream end - first content)` 计算。

| 工作负载 | 输出 token 数 | 解码速率 | 中位数 | 首个内容延迟中位数 | MTP 接受数 / 提议数 |
| --- | ---: | --- | ---: | ---: | ---: |
| 中文 | 128 | 18.52, 18.71, 19.85 | 18.71 tokens/s | 0.318 s | 244 / 2,496 (9.8%) |
| 代码 | 256 | 58.66, 61.09, 53.04 | 58.66 tokens/s | 0.305 s | 676 / 1,616 (41.8%) |
| JSON | 15, 15, 20 | 53.76, 53.64, 71.71 | 53.76 tokens/s | 0.323 s | 49 / 96 (51.0%) |

固定为 256 token 的代码吞吐量请求因达到长度上限而结束，语法上不完整。
另一次独立请求采用 512 token 预算并正常停止，在输出 287 个 token 后于 5.14 秒完成。
移除 Markdown 代码围栏后得到有效的 Python，包含所要求的三个断言；这些断言未执行。

三个 JSON 响应均可解析，且值与请求完全一致。短响应的解码速率对流式传输和停止计时
高度敏感，不应解读为持续吞吐量。

尽管 temperature 为零且使用固定种子，三次测量的中文响应出现三个不同哈希，代码响应也是三个，
JSON 响应则为两个。观察到的非确定性可能与多种批处理、QSA 和推测采样路径有关；
这一现象本身不足以证明单一原因。不过，上述未生效的 top-k 环境开关仍是值得单独排查的配置问题。

厂商产品页给出的单路流式速率范围是 59–116 tokens/s。代码测试的中位数接近其下限，
而中文提示词远低于该下限，因为 K16 接受率仅为 9.8%。提示词、生成文本和接受率
都会显著影响推测解码速度，因此产品页范围并非单一的保证速率。

## 八请求并发

三批测量之前先执行了一批预热。每批同时提交八个代码工作负载副本，各输出 128 个 token；
服务端禁用了前缀缓存。汇总解码速率统计从首次内容事件到最后一路流完成之间交付的全部 token。

| 批次 | 汇总解码速率 | 批次总耗时 | 单请求解码速率中位数 | 单请求 TTFC 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 138.43 tokens/s | 8.80 s | 37.39 tokens/s | 3.34 s |
| 2 | 125.95 tokens/s | 8.61 s | 35.24 tokens/s | 2.44 s |
| 3 | 135.84 tokens/s | 8.01 s | 37.51 tokens/s | 2.35 s |

汇总速率中位数为 135.84 tokens/s；MTP 在 6,000 个提议 token 中接受了 2,855 个（47.6%）。
这一结果位于产品页给出的八请求 108–313 tokens/s 范围内。单请求 TTFC 介于
0.53 至 5.69 秒，因为八个请求并未同时进入调度器。

## 预填充与上下文容量

预热后的三次请求使用普通文本提示词，API 测得其长度为 5,001 个 token，随后输出 32 个 token。
前缀缓存仍禁用。端到端首次内容延迟分别为 2.862、2.945 和 2.948 秒，中位数为 2.945 秒。
另一次请求的 Prometheus 增量显示预填充阶段耗时 2.577 秒，即计算速率为 1,940 tokens/s；
排队时间约为 31 微秒。

产品页报告 5K 上下文下 TTFT 为 2.5 秒、预填充速率为 2,589 tokens/s。
本地 TTFT 约慢 17.8%，内部预填充速率约低 25.1%。由于无法确认准确文本、分词方式、
计时边界和软件构建版本是否一致，这只是观察值对比，而非受控回归测试。

一次接近上限的请求包含 260,001 个输入 token 和一个输出 token，执行成功。
完整 HTTP 请求耗时 175.73 秒；vLLM 将其中 174.95 秒归于预填充，计算速率为
1,486 tokens/s，排队时间可忽略。输出 token 未产生非空的流式文本，因此不将其标为 TTFT。

在该请求期间，175 个活跃的一秒 GPU 样本的平均利用率为 97.71%，报告的平均 GPU 功率为
49.74 W。观察到的 GPU 峰值功率为 51.31 W，峰值温度为 59 C。这些数据不包括整板功率。

一个构造出的超出部署窗口的请求在推理前于 0.72 秒内被以 HTTP 400 拒绝。
错误信息明确指出总上下文上限为 265,000 token。因此，内部 320K 模型视图
并不意味着该部署对外提供 320K 上下文。

## 推理运行中的进程快照

在另一次八请求负载期间采集了 root 级进程快照。采集时，vLLM 报告四个运行中的请求、
四个等待中的请求，抢占次数为零。随后八个请求均在达到 4,096 token 上限时以 HTTP 200 完成；
该负载用于在检查时保持运行时活跃，不作为额外性能结果。

当时 Qwen 容器中有五个进程：

| 角色 | 进程 | 线程数 |
| --- | --- | ---: |
| 容器初始化 | `docker-init` | 1 |
| 运行时引导与信号转发包装进程 | `bash` | 1 |
| vLLM OpenAI API 前端 | `vllm.real serve` | 66 |
| Python 多进程资源跟踪器 | `multiprocessing.resource_tracker` | 41 |
| 模型执行进程 | `VLLM::EngineCore` | 134 |

完整主机快照包含 484 个进程和 1,279 个线程。私有采集结果还包含 root 可见的完整命令行、
可执行文件映射、进程树、Docker 进程列表、cgroups、命名空间、套接字及同期的 `tegrastats` 样本。
这些原始文件保存在公开仓库之外，因为全主机列表包含环境特定标识符和无关服务的命令行。

## 测量现状与后续工作

这些数据足以初步记录固定版本官方应用的单路流式表现、八请求调度、5K 预填充、
多模态冒烟检查及接近上限时的容量。值得开展的后续工作包括：

1. 追踪 QSA 选择器的执行，并将随包提供的选择器与已验证的确定性 SM110 实现比较。
2. 在完全相同的输出文本或受控 token 路径上比较 K1、K3 和 K16；当前 K16 结果随接受率大幅变化。
3. 分别测试应用的 128K 和 320K 部署选项，不要根据此 265K 配置外推。
4. 增加结构化工具调用、推理测试，以及覆盖更广的图像集。
5. 在单路和并发解码期间采集整板功率和风扇 RPM。

原始请求元数据、计数器和遥测数据保存在公开仓库之外。

## 2026-10-02 重部署（模型制品 0.1.8）

微服本体缓存 LPK 仍为 `0.1.48`，本次更新的是模型制品与运行时：安装包包含
`qwen-3.8-flash-next-t5000-0.1.8.tar`（9.93 GB 包装）与解包后的
`target/` 工件（约 118 GiB：9 片消融后 NVFP4 主体、8 片 `model-plefp8-*`
PLE FP8 权重及脚本）。部署完成后算力舱运行时镜像为
`registry.lazycat.cloud/catdogai/qwen38-flash-next:runtime-124-0.1.8`。

### 背景：长上下文多语言漂移

上游开发者博客披露，未审查版在长上下文下出现多语言乱码，归因为两处精度
损失：GDN 循环状态使用 BF16，舍入误差随生成长度与层数累积（逐层对比显示
相对误差从第 0 层约 0.017% 增长到第 43 层约 12.69%）；量化的 lm_head 扰动
相近 token 的概率排序并在自回归中放大。修复为 GDN 状态恢复 FP32、lm_head
使用原生 BF16（主体保持 NVFP4），修复后连续生成约 1.1 万 token 未再漂移，
代价是显存占用增加、并发容量与速度下降。博客建议生产使用原版量化，破甲
仅作研究用途；该部署因此处于被上游搁置的状态。

### 分发链路

- 下载器为 aipod_backend 容器内的 aria2c（RPC 模式），任务 URL 形如
  `https://modelscope.cn/models/manateelazycat/Qwen3.8-Flash-Next-NVFP4-PLEFP8-20653659/resolve/3e0e2711…/<file>`，
  302 重定向到 `cdn-lfs-cn-1.modelscope.cn` 的 LFS 对象存储。安装时
  HF/ModelScope 可选，本次选择 ModelScope 以节省跨境流量。
- 仓库名内嵌基线修订短哈希 `20653659`，任务固定到新修订 `3e0e2711…`，
  与 27B 镜像仓的"老工件新修订"模式一致。但该仓为 Lazycat 自建
  （无 `MIRROR_SOURCE.json`），且新修订的文件哈希（`config.json`
  `35ce005b…`、`tokenizer.json`、`model-plefp8-00000` `f8fbc923…`）与 HF
  `gorbatjovy/qwen3.8-flash-next-abliterated-NVFP4-plefp8` 当前工件
  （`caa1e829…`、`9328ce9c…`、`908fa3c5…`）全部不同，`3e0e2711…` 在该 HF 仓
  也不存在——0.1.8 是重新生产的工件而非同修订重分片。上游 HF 链条：
  `windowsxp811203/Qwen3.8-Flash-Next-Abliterated-NVFP4`（消融本体，
  @ `ed55beec…`）→ PLE FP8 重排 → `gorbatjovy/…-plefp8`（基线工件，
  @ `2065365912…`，未变）。
- 工件先落到用户网盘（每份文件附 `.aipod-verified.json`，记录 path、size、
  sha256，不含来源 URL），再传入算力舱。
- `target/` 同时携带消融工具链：`apply_ablation_flashnext.py`（CPU/BF16 执行
  消融，标注 `lm_head_untouched: True`、n-gram 表不动）、`graft_nvfp4.py`
  （NVFP4 主体嫁接）、`fix_nvfp4_config.py`（修复 modelopt 导出丢失的多模态
  config 包装，恢复 `qwen4_exp` 架构与 vision 配置）。README 记载 base 为
  `windowsxp811203/Qwen3.8-Flash-Next-Abliterated-NVFP4`，PLE 表改 FP8 存储
  重排后 173.6 → 125.9 GiB。
- 本次部署曾于 15:22 因网盘空间耗尽失败（`No space left on device`），事故
  损坏三个分片的 `.aria2` 控制文件（0 字节），导致重试在 2 秒内
  `Download aborted`；清除损坏的 `.part` 与控制文件后重试成功。旧版
  0.1.6 tar（约 133 GiB）仍留在网盘。
- 下载来源在安装时可选（HF/ModelScope），但**缓存优先于来源**：19:32 的
  一次未清空现有部署的 HF 源重装中，安装器按清单 sha256 校验网盘已有工件
  直接通过（这些文件此前由 ModelScope 下载），全程零下载，也未产生新的
  容器槽位（同名 compose 项目重建 `qwen38-flash-next-qwen-1`）。要观察
  HF 的真实下载链路，必须先清空网盘中的 0.1.8 工件目录。
- LPK 0.1.48 → 0.1.51 升级于 19:47 触发（控制面镜像
  `0e8678f9…` → `edb7caf1…`），升级期间微服对既有工件做全量校验导致
  sshd 饿死约两小时。升完在 22:0x 重部署：aria2 零任务、Pod agent 日志仅
  "all preloaded images are available locally"，0.1.51 的专用仓库与钉扎
  机制把未审查版 0.1.8 制品解析到与之前相同的 `runtime-124-0.1.8`，
  属防御性修复（防止未审查版与原版运行时元数据互相覆盖），未更换运行时。
  注意 LPK 升级不会重启 Pod 上已运行的服务容器。
- **缓存共三层**（当晚以 HF 源实测确认）：① 用户网盘的工件目录
  （`AI 模型/T5000 …/`，为"以后快速安装"暂存）；② 算力舱本地按检查点
  修订版组织的权重缓存
  `/var/lib/lzc-ai-agent/data/qwen38-flash-next/models/<checkpoint-rev>/`
  （0.1.51 升级时由网盘预置，目录名以检查点修订 `2065365912…` 为键，
  与下载源修订无关）；③ 算力舱上的运行时镜像。部署只在三层全部未命中
  时才真正下载。
- **HF 源实测**：清空①并临时挪走②后，HF 部署的下载计划为
  `https://huggingface.co/gorbatjovy/qwen3.8-flash-next-abliterated-NVFP4-plefp8/resolve/2065365912…/<file>`，
  总量 126 GB——即原始 HF 仓按基线同款修订钉扎；而 ModelScope 源走
  `manateelazycat/Qwen3.8-Flash-Next-NVFP4-PLEFP8-20653659` @ `3e0e2711…`
  （Lazycat 自家重导出，与 HF 原件哈希不同）。两个来源的制品**不是同一代

  （`snapshot/daily/beacon/document/`）会钉住已删除工件的空间，清缓存时
  需一并处理。

### 服务参数变化

引擎仍为 vLLM `0.0.0+18f658bb3185`（Torch 2.11.0、Transformers 5.12.1、
FlashInfer 0.6.18 均未变）。相对基线的变化：

| 设置 | 基线 0.1.40 | 本次 0.1.8 |
| --- | --- | --- |
| Mamba/GDN 循环状态 | BF16 | `--mamba-ssm-cache-dtype float32` |
| 输出头 | NVFP4 候选优先 | 原生 BF16（FP8 实验安装但 `enabled=False`） |
| KV 容量 | 351,829 token | 271,973 token（同一 12.8 GiB 分配） |
| 工具解析器 | Qwen3 工具调用 | 显式 `--tool-call-parser qwen3_coder` |
| 启动健壮性 | — | 新增预热与超时环境变量（warmup targets、`VLLM_USE_BREAKABLE_CUDAGRAPH=1`、ready timeout 1800 s） |

未变的参数：模型名 `qwen-3.8-flash-next-uncensored`、265,000-token 硬上限
（320K YaRN 视图）、8 序列、8,704 批处理 token、禁用前缀缓存、一层 MTP
K16、CUDA Graph FULL_DECODE_ONLY 捕获 [1, 17]、PLE FP8 内存映射（32 线程、
固定内存、2,048 行分块）、默认采样 0.3/0.95/20。

KV 容量下降 23% 即博客所述显存代价的直接体现：同一 12.8 GiB 下仅能容纳
约 1.03 个完整 265K 请求（基线 1.33 个）。

### 基准复测（2026-10-02，性能风扇）

负载提示词、输出上限（中文 128/代码 256 固定长度、JSON 自然停止）、温度
为零、禁用思考、预热与计时口径均与基线一致；种子固定为 42（基线未记录）。
接受/提议 token 取 Prometheus 计数器增量。

#### 单流

| 负载 | 输出 token 数 | 解码速率 | 中位数 | 首个内容延迟中位数 | MTP 接受 / 提议 |
| --- | ---: | --- | ---: | ---: | ---: |
| 中文 | 128 | 11.85, 12.17, 13.26 | 12.17 tokens/s | 0.362 s | 226 / 2,496 (9.1%) |
| 代码 | 256 | 36.20, 36.89, 34.21 | 36.20 tokens/s | 0.383 s | 665 / 1,696 (39.2%) |
| JSON | 15, 15, 15 | 35.23, 34.53, 34.52 | 34.53 tokens/s | 0.378 s | 48 / 96 (50.0%) |

相对基线：中文 −35.0%、代码 −38.3%、JSON −35.8%，而 MTP 接受率基本持平
（9.1%/39.2%/50.0% 对 9.8%/41.8%/51.0%）——速度损失来自 FP32 状态与 BF16
输出头的每步开销，而非推测解码失效。首个内容延迟 0.36–0.40 秒（基线
0.305–0.323 秒）。

#### 八请求并发

| 批次 | 汇总解码速率 | 批次总耗时 | 单请求速率中位数 | 单请求 TTFC 中位数 | 接受 / 提议 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 58.38 tokens/s | 18.01 s | 32.56 tokens/s | 7.533 s | 938 / 1,968 (47.7%) |
| 2 | 58.82 tokens/s | 17.90 s | 33.98 tokens/s | 7.520 s | 950 / 1,952 (48.7%) |
| 3 | 57.17 tokens/s | 18.35 s | 32.09 tokens/s | 7.513 s | 943 / 2,016 (46.8%) |

汇总速率中位数 58.38 tokens/s，比基线 135.84 低 57.0%；批次耗时从约 8 秒
增至约 18 秒。单请求解码速率中位数仅降约 10%（32–34 对 35–37.5 tokens/s），
但单请求 TTFC 中位数从 2.35–3.34 秒升至 7.5 秒，`request_queue_time_seconds`
累计 215 秒（100 个请求）：请求明显排队而非并行解码。结合
`kv_cache_max_concurrency=1.03` 与 FP32 GDN 状态池，判断并发车道被状态
容量压缩；确切池大小未从指标中核实，记为现象。

#### 预填充与上下文容量

5,001-token 提示词 + 32 输出 token：首个内容延迟 3.027、2.996、3.287 秒，
中位数 3.027 秒（基线 2.945 秒，+2.8%，基本持平）。

260,001 输入 + 1 输出成功完成，整请求 179.14 秒（基线 175.73 秒），计算
速率约 1,451 tokens/s（基线 1,486）。遥测覆盖 472 个一秒样本：`VDD_GPU`
平均 45.62 W、峰值 51.73 W（基线 49.74/51.31 W），GPU 温度平均 56.68 C、
峰值 61.91 C（基线峰值 59 C），系统 RAM 平均 113.7 GB、峰值 113.8 GB。
265,001-token 请求在推理前被 HTTP 400 拒绝，上限仍为 265,000 token。

#### 小结

精度修复（FP32 GDN 状态 + BF16 lm_head）的代价集中在解码侧：单流
−35~38%，八请求并发聚合 −57%（排队导致）；预填充几乎不受影响。与上游
博客"并发量和生成速度有所下降"的描述一致且幅度更大，支持其"破甲仅作
研究用途"的结论。
